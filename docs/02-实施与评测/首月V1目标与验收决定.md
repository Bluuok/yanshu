## 1. 不变约束和完成度

- 选择 **C：较完整的本地科研工作流 V1 测试版**。论文和实验规划是并列的首月核心验收路线；不能以单个演示、只有结果段落或仅有日历来替代。
- **连续 30 个自然日**作为首月冲刺窗口；预期 Day 1–23 主要开发与联调、**Day 24–30 完整七天**用于真实使用测试、回归、修复、科研效果与 UI/视觉/动效改进。不得把主要未开发功能隐性排入最后一周。
- 研发 **两人，能力接近**，分工及关键路径应平衡；交叉评审。导师负责必要的科学评审，不按全职开发人力计算。
- 首月现金采购**上限 4,000 元，不调整预算结构或采购授权**；本文不作采购选型。完整 RSI、生产级多租户、真实仪器直接控制和投稿质量保证均不属于首月承诺。
- OpenScience 是坚持优先使用的主运行底座；其技术调用方式、Fork 程度与具体 SDK 待实施文档和实测决定。若发现数据安全、不可复现或不可调用的阻断点，**不得以“坚持使用”为理由绕过验收**，先局部修复并把阻断事实升级给负责人。
- **部署目标**：Ubuntu Linux 实验室工作站承担运行与科研计算，Windows 客户端可访问研枢工作台。首版不承诺 Windows 本机独立运行全部执行后端；远程访问的认证、传输和授权必须实测。
- **工作台目标**：在 OpenScience 原有前端基础上修改并增设研枢 UI；不仅是接两个页面，还包含一致的视觉、合理动效、实验甘特图与科研证据/任务查看能力。实现方案另经技术评审，不把“美化 Skill”直接视为已经交付可维护前端。
- **数据库目标**：SQLite 单机 V1，实体边界、项目归属与版本规范明确。未来多用户/多租户需可扩展，但**首月不实现生产级租户隔离或并发服务**。

## 3. 两条业务线的 Day 30 功能验收

### A｜材料实验论文工作流

**输入**：研究目标、目标期刊及稿件类型、已授权的真实原始实验数据/方法、允许引用的文献与已有图表。

**必须能走通**：授权数据登记与不可变归档 → 字段、单位及缺项检查 → Python 复算与图表 → 文献来源定位、正文论断关联 → 主要章节初稿（Introduction、Methods、Results、Discussion、Conclusion 等按稿件类型适配） → 独立核查与定点修订 → 持久保存、再次打开 → Word 和 LaTeX 可编辑导出及已选期刊样式适配。

**资料不足**：每个缺项标注对受影响章节/结论的影响，按优先级主动向研究者索取具体字段、材料或批准；在无新增资料时不编造，允许生成明确标示缺项的稿件，不能把它判为“内容质量已达标”。

**验收证据**：一份数据包的文件/脚本/图表/数值/引文完整关联；一份结构化初稿及修订 diff；DOCX 可打开编辑、LaTeX 源可检验；至少一组基于正式官方作者指南的期刊格式规则包和至少两种可选择的格式配置测试（若导师尚未确定具体期刊，选择范围作为待确认，不能宣称所有期刊均支持）。按《论文评分》独立给出八维指标、覆盖率、硬性错误与人工修订工作量。

### B｜动态实验规划工作流

**输入**：研究目标、实验方法与工艺条件、设备/人员/时间约束、实验反馈、新数据，以及哪些方法参数已获研究者确认。

**必须能走通**：实验设计/对照建议 → 含前置依赖和时间窗的计划 → 设备/工艺硬约束检查 → 研究者确认生效 → 完成/延期/失败/新结果反馈 → 仅调整受影响任务并保留版本差异 → 审批激活新计划 → 应用运行时触发提醒与待办、撤销过时提醒、去重、重启后补处理。

**科研边界**：LLM 提建议，不是科学条件的唯一裁决者；已确认工艺下限不因排期被压缩。研究方向、重要实验步骤与危险操作须交研究者；任何模拟进度/实验结果都清楚标记为模拟，不能伪装为已完成事实。

**验收证据**：有环依赖被拒绝、设备冲突可解释、工艺时间不可违背、一次延期及一次失败/结果分支后计划版本对照、未批准版本不激活、提醒不重复且旧提醒取消、研究人员能查看/修改并恢复计划。甘特图必须能显示任务、时间、依赖、资源冲突与版本差异；不以仅生成静态图片代替业务视图。

### 共用能力

项目/任务/结果保存再打开，执行 ID 和业务任务分离，源文件真正只读、输出独立且带 SHA256，审批范围可追溯，执行中断后核对副作用，模型/工具调用基本记录，开发与隐藏评测数据隔离。**平台运行成功、科研结果正确、科研质量达标分别给出结论**。

## 4. 最小交付等级

- **MUST（缺一则 V1 未完成）**：双路线完整功能路径；真实且有授权的数据与来源；结构完整的有据论文初稿、缺项问询、独立核查、双格式及期刊选择；计划依赖/约束/反馈/版本/审批/运行时提醒；文件隔离、持久化、科研事实与工程记录；Ubuntu 运行及 Windows 访问；必要的 OpenScience UI 改造及可操作甘特图；独立软件与科研质量验收。
- **SHOULD（在满足 MUST 后继续增强）**：复杂调度求解器、丰富的微交互与动画、更多期刊和图表主题、多案例科学质量覆盖、优先级自动建议、多轮模型对比。
- **LATER（不阻断首月）**：生产级多租户、离线/关机仍跨设备发送提醒、移动推送、多节点调度、真实仪器自动控制、模型自我修改、所有期刊完整投稿包。

设计允许用成熟第三方能力交付 MUST，但不得以“已安装 Skill/库”取代真实操作与验收。

## 5. 验收时区与时间口径

- Day 1 是负责人宣布开始的**自然日**。连续 Day 1–30，所有七天均计入冲刺；实际日历日期在启动时填入，不用虚构启动日期。
- Day 24–30 是**完整七天**测试周；明确为稳定、改进与试用，不应继续大规模追加主功能。
- G1/G2：Day 5 前真实样本、核心调用、Ubuntu 文件与会话安全、Windows 可访问性均须产生可查日志；未过的项报告为阻断问题。
- G3：Day 17–23 两条业务功能冻线并提前联调，检查论文链路、反馈排程、版本审批及导出。功能冻结不等于科研质量已经达标。
- G4：Day 24–30 重复操作、错误注入、故意中断、试用、视觉可用性和科研效果对照。记录真实失败、回归结果和人工修改时间。
- 科研分数未达导师批准阈值时：归入**科研质量不通过**，定位问题、有限迭代并再次评分；不可无限 Agent 自循环、擅自变更阈值或用高平均分覆盖严重科研错误。30 天到期仍未过，应如实标记，后续继续科研质量改进，不得冒充通过。

## 6. 研发分工原则与实施待决

两名研发都承担实际业务代码、测试与联调。Day 1–5 共同确认接口/目录/测试样本；随后采用**两个均衡工作包**：一人主责论文数据/证据/导出与部分 UI，另一人主责计划/约束/版本/甘特图与部分 UI；OpenScience 接入、SQLite、权限及集成按技能均分并互相审查。真实工时和接口分配由《开发实施方案》确定，不指定某人永远承担所有平台任务。

**需另行技术评审的事项**：OpenScience 前端深度修改方案、SDK/Fork 取舍、Ubuntu/Windows 认证和网络拓扑、具体甘特图库与 Skills、Langfuse 部署/费用/隐私、第一批期刊和材料样本、导师评分阈值。产品决定已明确，不得把未验证技术假设伪装成事实。
