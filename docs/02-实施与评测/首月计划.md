# 研枢科研智能体平台｜首月四周实施与预算计划

**文件性质：** 首月立项执行与阶段验收计划（建议 V1）  
**适用期限：** 启动批准日起连续 4 周；实际日期由项目负责人填写  
**首月现金采购上限：** **¥4,000**（不代表整个第一阶段经费）  
**人力假设：** 2 名研发人员分工，导师进行关键科研判断；已有人负责 RSI，不纳入本月核心交付  

## 一、首月目标与边界

### 1.1 首月交付目标（结果导向）

在单机 Windows + 本地文件条件下，**验证一套可二开的科研工作流底座，完成两条科研路线的最小可运行样例，留下可复算的科研数据与可检查的运行记录。**

- **平台：** 官方 OpenScience 安装并验证源码扩展；通过关键门槛后，才决定是否 Fork 为唯一主二开仓库。失败则及时评审备用技术路线，不同时建设多套主框架。
- **论文路线 A：** 完成“真实实验数据 → 校验/计算 → 图表或结果段落 → 来源记录 → 基础审查”的**局部贯通样例**。首月不承诺完整论文初稿。
- **实验路线 B：** 完成“研究目标/约束 → 含前置依赖的初版实验计划 → 一次模拟延期或资源冲突 → 计划调整示例”。提醒可先做应用内事件模拟；稳定定时触发与正式通知属于后续完善项。
- **数据与评测：** 实际验收至少 1 套公开材料实验案例，建立一份可复用任务输入包/隐藏评测包以及基本事实与引用检查清单。输出原始数据版本和各次实验日志，不把目标论文直接提供给执行 Agent。
- **采购与安全：** 4,000 元是本月**最高采购额度**，不是必须支出；先按小额试用/按需充值推进，禁止未授权数据外传。

### 1.2 本月明确不承诺

不承诺完成整篇投稿级论文、正式上线给外部用户、自动真实实验或工业仿真、多租户安全系统、完整 RSI、自研全套 PDF/检索/监控基础设施。第一阶段全程仍以论文质量和动态实验规划为两条业务主线；首月先验证底座、材料、流程，第二个月再扩为端到端交付。

## 三、每周工作任务、交付物与量化验收

### W1｜材料与基线准备：先证明“能测试什么”

**研发 A（底座）：** ①用 Windows 安装 OpenScience 官方版，记录版本、启动步骤、依赖、模型连接及问题；②使用低成本模型完成一次输入/输出与工具调用；③核对源码结构、插件/MCP/Skills 路径、开发方式和许可证；④确定后续任务与产物目录。

**研发 B（科研与 Eval）：** ①从现有 12 篇候选论文优先选择 MAT-001/002/003，至少下载、解压并核验 1 套论文—数据关联材料；②记录来源链接、许可证、SHA256、字段、单位、记录数和缺口；③整理一份“允许输入的材料”和“仅评测端可见的论文/答案”；④拟定 5 条关键数值/事实检查和 5 条引用核查样例；⑤用固定输入完成一次直接模型基线，保存原文输出与用量。

**本周交付：**《首批样本验收卡》×1、《OpenScience 体验及源码观察记录》×1、《直接模型基线记录》×1、工作目录与密钥权限清单。

**G1 最低门槛：** 已实际读取并核验 **≥1 套真实实验数据**；至少 **1 次可复现的模型调用**；目标论文及答案与执行输入分开保存；有基本费用与问题记录。若公开原始数据不可用，不硬标 A 类，改选另一套可核验案例。

### W2｜选定底座并搭任务骨架：优先少改上游

**研发 A：** ①在本机成功启动 OpenScience 源码/开发模式；②增加 **1 个小型自定义工具或 Skill**（优先“实验数据字段/单位核验”）；③验证项目任务卡、文件版本、执行记录和失败重试；④检查能否暂停/恢复同一任务、是否存在重复写入风险；⑤在 G2 前决定继续 Fork 或触发备选评估。

**研发 B：** ①对 PaperQA2、Docling/GROBID、K-Dense 选少量候选进行**接口与质量验证**，只接本月实际需要的一种检索或解析能力；②建立可执行科研任务的最小输入/输出数据合同；③完成目标论文参考答案与关键实验结果的独立核对表；④针对一份论文记录至少 5 个可追溯来源位置。

**本周交付：**《主底座二开决策记录》×1、可运行最小任务工程×1、科研工具/Skill 接入样例×1、数据合同与核查样例×1。

**G2 最低门槛：** 一条任务能从“输入文件 → 调用工具/模型 → 保存产物与日志”运行；新增能力不要求重写上游主要执行循环；关键异常可以查看原因；明确“采用 OpenScience / 暂缓并评审备用方案”的书面结论。若源码无法按期运行，优先收敛可运行最小骨架，而非无限期折腾底座。

### W3｜两条业务路线的最小垂直切片

**研发 A：** ①把数据处理、基础文献检索或引用核验配置为受控工具调用；②实现任务步骤状态（待处理/已完成/需补材料/失败）；③制作实验计划任务依赖结构；④模拟一次延期或设备不可用后，只更新受影响的计划任务，保留前后版本。

**研发 B：** ①对 1 套真实材料数据执行实际统计或计算并输出 **至少 1 张可追溯的图/表**；②用确认的研究目标、数据和出处生成一个**论文结果段或方法段草稿**，不强求全文；③检查至少 5 项数字/单位与至少 5 项引用或来源定位；④编写实验计划中的约束和依赖示例，核对模型未把“计划”写成“已完成实验”。

**本周交付：** 论文局部结果包（数据、代码、图、段落、来源）×1；实验计划及变更记录×1；基本审查记录×1。

**G3 最低门槛：** 科研计算能够回溯到文件/脚本/结果；至少 1 个结果段落带有明确待核清单；实验计划可见前置依赖，并能显示**1 次模拟变更前后差异**。出现伪造结果或无法解释的数据，应直接标记失败并整改，不计作流程完成。

### W4｜联调与首月验收：展示真实效果，而不是凑功能数量

**研发 A：** ①整合两条路线的最小流程；②补充运行日志、基本预算/Token 记录和异常处理；③执行一次故意中断后的恢复试验；④验证一次应用内提醒或提醒事件**去重**；⑤整理环境启动说明、版本和下一月技术待办。

**研发 B：** ①使用同一组真实实验材料比较“直接模型”与“已有 Skills/工具/流程”两种结果；②按《论文评分.md》选择适用条目出具**试评分，不强行给缺数据的项满分**；③记录至少 10 条可核查的科研事实/引用检查结果以及人工修订位置；④联合导师或研究人员审阅 1 次，不能获得专家反馈则明确标记“待专家核验”；⑤整理下月样本扩充计划。

**本周交付：** 首月演示录像或可复现演示说明×1；论文路线样例×1；实验规划样例×1；初版评分/对照报告×1；问题与风险清单×1；费用和后续里程碑报告×1。

**G4 最低门槛：** 两条路线都有**可再次运行的样例**；数据没有虚构、原件未覆盖；关键成果和异常能追溯；至少一项科研效果对照具有数据/人工核验依据；实际支出有可对账凭证。**G4 为原型通过门槛，不等于论文质量达标或第一阶段完成。**

- **Modelink（2,000）**：作为首月主推理费用池，建议按量模式分批充值或设置用量预算，不先承诺一次性花完。七牛官方提供账户余额、Token 用量、请求日志、API Key 限额等管理能力；**包月订阅与按量余额不是同一种预算**，订阅周刷新额度、过期不结转，不能混算。

- **Command Code GOAT×4（300）**：原预算暂保留 4 个独立账号的上限，但**研发假设仅 2 人**；应先确认是否确有 4 名独立获授权使用者。若只有 2 人，就只为实际用户购买所需数量，剩余额度暂不释放，不为花预算强制购买。
- **OpenCode Go×1（80）**：官方 Go 为 **$10/月** 的编程订阅；限额随套餐与模型变化。它属于开发工具，不应计为研枢后端可无限使用的科研推理额度。
- **DeepSeek 直充（20）**：用于直连联通性/兼容性与故障定位，实际模型、搜索/抓取 API 单价以官方控制台为准。
- **文献检索（200）**：先用开放接口/免费范围或已有账户，只有需要提高全文可得性、解析质量或请求量时才支付；不得把“购买了检索”当成“获得了全文版权”。
- **机动额（100）**：需注明原因、预期改进与审批人，优先处理必要集成缺口；不用则保留。

### 4.3 采购审批、发票与风险控制

1. **批准额度 ≠ 预付到账 ≠ 已消耗费用**。项目台账分别记录三者和结余；每周公布累计采购、累计实际用量及下一周申请。
2. 项目/开发者 API Key 分离，启用平台可用的配额、IP 白名单/模型范围控制，记录模型名、费率与请求量；限制错误循环的最大重试次数。
3. 当某周实际使用量不及预计时，下一周**优先使用旧余额**，不得为满足周预算表重复充值；服务支持的免费额度优先使用。
4. 购买 GOAT、OpenCode 等订阅前先核对是否限定个人使用、是否支持商业开发、是否需要独立账号；不共享账号。境外支付金额与税费由账单核对。
5. 工作台和原始实验资料默认本地，不采购云服务器和云存储；但 API 请求可能出境，未获授权的敏感科研资料不得发送给外部供应商。
6. 与公司报销有关的订单、付款记录、消费账单、可用发票及授权条款必须保存。MaiToken 与其他平台的开票条件以购买时可核实的合同与控制台为准。

## 五、月末验收评分卡与决策

| 验收项目 | 必须展示的证据 | 首月建议判定方式 |
|---|---|---|
| **真实样本** | 论文 DOI、数据下载记录、文件散列、字段/单位/许可 | 至少 1 套被逐文件核对，信息不完整如实标记 |
| **底座可二开性** | Windows 运行日志、源码运行方式、小工具接入与异常记录 | 有书面采用/否决结论；不能只有产品演示截图 |
| **论文局部流程** | 数据→计算脚本→图表/结果段→引用/来源 | 能重新执行，并识别错误数据或缺失证据 |
| **动态实验规划** | 初始依赖计划、模拟延期/冲突、变更差异 | 有至少 1 次可解释的局部调整，不伪称真实实验执行 |
| **质量与真实性** | 适用的论文量表子项、10 条以上检查记录、重大错误记录 | 有分数来源和 N/A 说明；不预设未校准的“80 分合格” |
| **成本和安全** | 充值/消耗/结余表、密钥权限、云端授权边界 | 未越预算、未失控循环、无未经授权外传 |
| **项目交付** | 可启动说明、样本与报告、演示脚本、风险及第二月任务 | 两位开发者可复现主要样例；不可复现则不算交付 |

**建议月末决策：** 若主底座通过 G2 且 G3/G4 样例可演示 → 保留唯一二开方向，第二月推进完整论文初稿、版本迭代和动态提醒；若底座失败但科研数据链路正确 → 在不丢失样本/Eval 的前提下更换运行底座；若数据不可核验或 AI 虚构重要结果 → 先停下修正事实与证据链，不用更多功能掩盖质量问题。

## 六、人员、管理节奏与主要风险

**研发 A：** 主底座、环境、扩展与状态/实验依赖、集成与恢复；**研发 B：** 论文数据验收、检索/计算/Skills、量化评分与质量报告；两人互相评审关键变更。**导师：** 核验科学判断、错误严重性及论文质量，不要求导师逐日参与。**RSI 独立成员：** 本月只对接接口边界，暂不列为关键依赖。

**会议与记录：** 周初确定 3–5 项可验证任务，周中同步阻塞，周末按照 G1–G4 验收并审批下一周；保留 GitHub Issue/PR、运行记录、消耗台账与失败原因。任务若连续两次失败，应缩小范围/换组件，不无限增加工具。

| 风险 | 具体表现 | 缓解措施 |
|---|---|---|
| 核心底座不可二开 | 本机安装可用但源码扩展困难、运行态不可恢复 | W2 必须做最小真实扩展；失败触发限时备选评审 |
| 论文数据不完整 | 仅最终论文或 Source Data，无原始数据定义 | 优先核验数据文件；只能做局部测试时诚实降级 |
| API 预算快速消耗 | 模型循环、无上限重试、重复查询、多平台预充值 | 开 Key 限额、按周释放、费用看板与任务预算 |
| 技能/工具集成过度 | 同时安装大量 Skills、多个 Agent Harness | 一次只引入一个经对照确有增益的组件 |
| 科研失真 | 数据单位错误、虚构实验、引文不支持结论 | 原始数据只读、计算复验、关键结论独立核验、必要人工审批 |
| 安全与费用授权 | 未发表数据出境、订阅范围不适合团队 | 首月只用公开案例，敏感输入本地分级，购买前审查条款 |

## 七、下个月与整个第一阶段的衔接
