# 研枢科研智能体平台｜30 天 V1 开发与验收计划

状态：依据 2026-11-10 负责人选择的方案 C 更新，目标已明确，软件尚未实现。团队按两名研发人员安排。首月现金采购上限 **4,000 元**，不代表必须消费完。这 30 天是第一阶段的首月软件 V1 交付安排，不是将整个第一阶段压缩为 30 天。后续仍保留扩充样本、科研质量优化、导师评测和缺陷回归。

## 一、V1 交付边界

第 30 天交付在 **Ubuntu 实验室工作站运行、Windows 可访问**、可保存和重新打开成果的 **两条完整业务工作流测试版**，不是只有论文结果段与实验日历演示。30 天是连续自然日；**Day 24–30 为完整七天的使用测试、修复和 UI/科研效果优化窗口**。详见 [首月 V1 目标与验收决定](首月V1目标与验收决定.md)。

- 论文工作流：导入有授权的真实材料实验数据与文献，计算和绘图，形成主要章节**有实质内容**、带证据及待核清单的初稿；缺资料时主动向研究者索取，不能编造；进行独立审查、定点修订，**先选择目标期刊及稿件类型**再匹配格式，导出可编辑 Word 和 LaTeX。具体深度及达标阈值见《论文评分》，由导师最终批准。
- 实验规划工作流：对真实科研目标提出实验设计/对照建议，在已确认的材料工艺、资源与时间约束下形成含依赖的计划；接受完成、延期、失败与新结果反馈，经确定性约束检查后局部调整并由研究者确认重要修改；保留版本、资源冲突与**可交互甘特图**，应用运行时调度提醒、重启后补处理过期事项。
- 共用能力：OpenScience 的 Agent 执行与**明显改造、美化的原有工作台**，研枢项目状态、任务恢复、独立科研证据、可配置材料规则、模型费用和授权记录；首月按受控埋点或已核验的 Langfuse 方案提供可定位的执行观测，观测技术栈待实际核定。
- 不纳入 V1：生产级多租户、真实仪器控制、工业仿真自动操作、RSI 自动改核心代码及确保论文满足投稿质量。两条路线各需至少一个真实或清楚标记模拟部分的可复现案例。

OpenScience 为负责人坚持的优先主底座，但版本、SDK/Fork 范围及前端二开方式仍待技术决策；G2 要在 Ubuntu 工作站及 Windows 客户端的真实环境验证。任何安全、授权和科研真实性阻断不得以固定底座为由跳过。

## 二、Day 1–30 排期与双人分工

**唯一时间口径：连续 30 个自然日，每天都属于冲刺窗口**；实际起止日期在负责人宣布启动时记录，**Day 24–30 全七天留给试用、回归、故障修复和体验/视觉/科研效果优化**，原则上不再追加大型功能。不同天的进展可以波动，但每个 Gate 按可运行证据判断。

| 阶段 | 开发主线（两人均投入业务代码，负载尽量相当） | 可检查产物和关口 |
|---|---|---|
| Day 1–5 | 研发 A 主责 OpenScience Ubuntu 运行/Windows 访问、受控文件与 API 冒烟；研发 B 主责科研样本/计算、SQLite 模型和任务/论文契约；双方共同完成界面初版与跨模块接口 | G1/G2：源数据授权及哈希；模型 + Python 真实调用；运行/任务 ID、只读输入/可写输出、会话中断与 Windows 访问；论文评分规则与待导师问题 |
| Day 6–11 | A：论文任务、来源/证据与期刊选择 UI、产物/导出接口；B：实验计划依赖/时间/资源与版本模型、甘特图最小可操作视图；双方用桩件联调 | 论文真实数据和计算图表能保存；计划可编辑显示依赖及资源；UI 已有统一视觉基线 |
| Day 12–17 | A：论文分章生成、引文/数值审查、补资料和双格式输出；B：实验反馈、局部重排、审批激活、提醒与去重；交叉评审质量与状态 | 双路线核心功能链开始端到端运行；一例资料缺失主动问询、一例延期/设备冲突和版本差异 |
| Day 18–23 | 双人完成长期科研成果保存/重开、故障恢复、证据与独立审查、Langfuse 或轻量 Trace 联通；统一前端美化和交互式甘特图、期刊规则包；修复集成阻断 | **Day 23 功能冻结候选**：双线完整、可重复、可编辑导出、可重启恢复，UI 关键操作完整；不得把大量未完成核心模块转到测试周 |
| **Day 24–30** | **七天完整测试周**：两人交叉执行真实科研任务与独立 Eval、负向安全/重复通知/恢复测试、导师或研究员试用、UI 视觉和动效打磨、关键科研质量错误迭代、缺陷回归、发布说明 | **G4**：软件功能/科研质量分别判定，记录八维分与导师阈值状态、材料/证据位置、人工修订时间、UI 试用意见、缺陷关闭或遗留及实际费用 |

**分工调整：** 不让研发 A 独担底座+数据库+排程+提醒+联调，也不让 B 只负责写材料和测试。两人分别主责论文与动态规划的关键业务模块，并共同承担前端改造、集成、安全和科研回归。最终源码模块分配由实施方案确认。

**技术门槛**：Day 5 如果 OpenScience 存在阻断问题，首先提出局部修复、明确不可放宽的数据安全与授权要求，并升级负责人裁决；不另开第二套 Agent Harness 并行主线。Day 23 若功能未冻结应真实披露并进入测试周的风险管理，不得取消七天测试周来隐藏延期。

## 三、首周 Day 1–5 操作与验收

| 日程 | 研发 A | 研发 B |
|---|---|---|
| Day 1 | 锁定 Ubuntu 工作站上的 OpenScience 与 SDK 候选版本，校验 capabilities、Windows 访问和 isolated/project 差异 | 核验候选真实数据、确定证据、人工审批和实验版本字段 |
| Day 2 | 建立三种运行 ID 映射、确定工作区及文件路径清单 | 明确来源和论断关系、审批有效期和计划版本字段 |
| Day 3 | 接入 Ubuntu Python 工具，验证 input 可读不可写、output 可写，并记录受控文件映射 | 使用真实数据复算输出、核验源文件与副本 SHA256 |
| Day 4 | 测试 SSE 断线、崩溃、重复请求、过期及越权审批拒绝 | 定义材料规则及论断审查，核对计划依赖和通知契约 |
| Day 5 | 联调、记录 G2 是否通过及阻断点 | 核验输入与输出哈希、科研记录与计算结果，整理样本验收卡 |

**G1**：至少一套候选真实数据的文件级检查完成并说明可测范围。

**G2**：Ubuntu 工作站上一次真实模型与 Python 工具调用可以完成且 Windows 客户端可访问，保存 sessionID/requestID/runID、session 工作区模式、实际 input/output 路径及文件映射；用受限工具主动尝试写 input，必须被系统权限拒绝，output 应可写且源文件 SHA256 不变；中断先核对副作用再重试，SSE 断线不重复提交，过期/越权审批不得生效。未实测成功应明确记录失败，不用模拟截图代替。

**G3（Day 23 前）**：实验反馈触发受工艺及资源约束的局部重排，新计划须审批后激活；新旧版本、甘特图、受影响任务、资源冲突和旧通知撤销可查，重复提醒按幂等键去重。论文路线主要章节具备来源证据、主动追问缺项、期刊选择及 Word/LaTeX 双格式导出，两个场景均可重复运行。

**G4（Day 24–30）**：两条端到端业务线能保存、继续编辑、导出或查看成果，完成真实使用和安全回归及视觉/动效体验复查，有来源与审查记录、调用观测、费用与缺陷台账。依据《论文评分》给出八维试评分、内容深度覆盖与导师批准阈值状态；**软件通过、科研质量通过/失败/待评估分别报告**，不能以功能完整替代科研正确性。

### 4.2 采购逻辑与现实修正

- **Modelink（2,000）**：作为首月主推理费用池，建议按量模式分批充值或设置用量预算，不先承诺一次性花完。七牛官方提供账户余额、Token 用量、请求日志、API Key 限额等管理能力；**包月订阅与按量余额不是同一种预算**，订阅周刷新额度、过期不结转，不能混算。
- **MaiToken（1,300）**：按原文保留备用 API 费用池，用于主通道异常、模型交叉核查及少量质量对照；仅在核对计费、实际可用模型、使用授权和发票条款后启用。其底层模型可能与主通道重合，不应把两者算作模型提供商级独立容灾。
- **Command Code GOAT×4（300）**：原预算暂保留 4 个独立账号的上限，但**研发假设仅 2 人**；应先确认是否确有 4 名独立获授权使用者。若只有 2 人，就只为实际用户购买所需数量，剩余额度暂不释放，不为花预算强制购买。
- **OpenCode Go×1（80）**：官方 Go 为 **$10/月** 的编程订阅；限额随套餐与模型变化。它属于开发工具，不应计为研枢后端可无限使用的科研推理额度。
- **DeepSeek 直充（20）**：用于直连联通性/兼容性与故障定位，实际模型、搜索/抓取 API 单价以官方控制台为准。
- **文献检索（200）**：先用开放接口/免费范围或已有账户，只有需要提高全文可得性、解析质量或请求量时才支付；不得把“购买了检索”当成“获得了全文版权”。
- **机动额（100）**：需注明原因、预期改进与审批人，优先处理必要集成缺口；不用则保留。

### 4.3 采购审批、发票与风险控制

1. **批准额度 ≠ 预付到账 ≠ 已消耗费用**。项目台账分别记录三者和结余；每周公布累计采购、累计实际用量及下一周申请。
2. 项目/开发者 API Key 分离，启用平台可用的配额、IP 白名单/模型范围控制，记录模型名、费率与请求量；限制错误循环的最大重试次数。
3. 当某周实际使用量不及预计时，下一周**优先使用旧余额**，不得为满足周预算表重复充值；服务支持的免费额度优先使用。
4. 购买 GOAT、OpenCode 等订阅前先核对是否限定个人使用、是否支持商业开发、是否需要独立账号；不共享账号。境外支付金额与税费由账单核对。
5. 工作台和原始实验资料默认本地，不采购云服务器和云存储；但 API 请求可能出境，未获授权的敏感科研资料不得发送给外部供应商。
6. 与公司报销有关的订单、付款记录、消费账单、可用发票及授权条款必须保存。MaiToken 与其他平台的开票条件以购买时可核实的合同与控制台为准。

## 六、后续工作与管理风险

30 天软件 V1 交付后，整个第一阶段仍继续科研质量优化、扩充真实材料案例、导师及专家评测与版本回归。首月未验证的科研能力如实保留为待完成项。


研发 A、B 能力相近，按论文链路与动态实验链路分担业务开发；二人共同承担 OpenScience 接入、界面大改、SQLite/权限、集成回归和科研质量验收，并互审关键修改。明确责任与实际人日分配留待开发实施方案。每周至少记录一次可运行结果、阻断问题和下周任务，使用 GitHub Issue/PR 保存证据。

材料标准与工艺规则需按实际测试方法选择并确认，不得填入固定的通用拟合区间、试样损耗率或不可解释的“准确率”。原始实验数据不能覆盖；本地未发表材料在授权核查前不能发往外部模型。OpenScience 会话轨迹分享与外发设置是 G2 的检查项。
