## 3. 哪些问题不需要挡住技术选型文档

- **待导师审议**：首批期刊及稿件类型、各章科学深度、八维质量阈值、材料工艺硬约束、实验数据合法使用范围。可先设计可配置接口、准备公开测试样本，但不得填入未经确认的科研规则、宣称分数达标或将研究者未知条件变成事实。
- **待产品负责人核对**：口述“long files”是否就是 Langfuse；实际 Ubuntu 主机配置、Windows 访问方式、两名研发可投入时间。只能把未经核实部分写为“待定/风险”。
- **后置**：大规模材料 Skills 目录、复杂求解器/多租户、第二套 Agent 底座、工业仿真自动控制、设备联动与 RSI 自动改核心；不得为这些目标提前搭建首月不需要的完整系统。

## 4. 技术选型评审的最低交付与实施顺序

1. **查现有能力**：按业务目标逐项对应 OpenScience 原生实现，引用官方源码/SDK、许可证和实际版本；区分“可调用 API/库/Skill”与“仅借鉴架构”。
2. **验证关键风险**：优先实测 Ubuntu—Windows 运行、前端可扩展性与甘特图、Python 与原始数据隔离、Word/LaTeX 导出、执行/审批恢复。可以进行短小的技术试验，不视为正式业务开发完成。
3. **冻结少量必要选型**：技术选择记录组件与版本、接口、替代选项、额外依赖与费用、验证结果、开放问题；不可验证的项保持“候选/待测”，不能强行作最终决定。
4. **再形成独立《技术选型与集成方案》**：作为技术选型权威文件，并以此和产品目标共同输入《开发实施方案》（代码目录、任务拆分、工时和 Day 1–30 落地计划）。

技术选型阶段需同步评估**两人主要开发约 23 天、最后完整 7 天测试**的实际容量。若产品 MUST 的工作量超过可用人力，应向负责人提交明确风险及可复用组件/范围调整选择，不得静默降低 PR #3 的产品目标或压缩测试周。
