# 研枢 V1 任务状态与安全恢复规范

版本：2026-11-06；状态：待实现。业务状态在研枢，Agent 运行状态在 OpenScience。

## 1. 状态定义

| 研枢状态 | 使用条件 | 后续处理 |
|---|---|---|
| PENDING | 已创建且必要输入已验证，未启动；或安全核对后允许重试 | 经授权启动 RUNNING；缺输入转 WAITING_FOR_DATA |
| RUNNING | 有正在执行或已接收的运行尝试 | 成功核验后 COMPLETED；缺资料或确认时暂停；中断时进入 RECONCILING |
| WAITING_FOR_DATA | 创建时就缺少关键输入，或执行后发现缺项 | 研究者补齐并校验后返回 PENDING；不需预先建立 Agent attempt |
| WAITING_FOR_CONFIRM | 重大实验修改、数据外发或科学争议待决 | 研究者批准后继续；拒绝则退出或修改方案 |
| RECONCILING | 请求结果不确定、执行崩溃或副作用未核清 | 核对回执和产物后完成、重试、失败或等待确认 |
| COMPLETED | 成果已保存，完成业务层的指定核验 | 终态；修订创建新版本 |
| FAILED | 已确认失败、封存原因 | 终态。研究者如需重试须新建 task_id，用 retry_of_task_id 关联原任务 |
| CANCELLED | 研究者或政策终止 | 终态 |

初次输入缺失时直接创建 WAITING_FOR_DATA 状态的任务，不应提交空输入给 OpenScience。FAILED 和 CANCELLED 视为业务终态，不允许 FAILED 直接跳回 PENDING；只有未终态的 RECONCILING 任务经过副作用核对后可以新增 attempt。

不能靠轮询、定时器或模型推测绕过 WAITING_FOR_CONFIRM。非关键参数缺失允许其他独立步骤继续；关键事实缺失才阻断相应步骤。

## 2. OpenScience 状态映射

OpenScience 接收请求可能处于 accepted、running、completed、failed、cancelled、interrupted。接收成功只表示任务被接纳。completed 只表示 Agent 回合完成；科研数据、图表、引用、产物提交和必要审批仍须独立核查。interrupted 不表示可以安全重做。

## 3. 安全执行与恢复

1. 任务下发前先保存 os_session_id、os_request_id、完整请求摘要及 PREPARED attempt。OpenScience 同一 session 的重复 requestID 可返回既有回执，但不能保证外部工具副作用只执行一次。
2. 保存返回的 os_run_id，使用同版本 SDK 的 Snapshot 和 SSE 事件观察；事件断档先重新取快照，不提交第二个 Prompt。
3. 若运行中等待权限或用户问题，先建立持久化 approval_requests，并保存任务版本、权限 scope、有效期、申请人、当前 Snapshot 序号和 os_pending_request_id。只有授权研究员能提交 approval_decisions；决定需要按 approval_id 和 decision_operation_id 去重。只对最新 Snapshot 中仍有效的 continuation 调用 runtime.decide，单独保存 OpenScience 决定回执或不确定状态。服务器崩溃后不能沿用失效的审批请求。
4. 发生进程退出、网络结果未知或 interrupted 时，设置 RECONCILING。检查已提交产物、文件 SHA256、外部作业状态与可能的副作用，再决定完成或重试。
5. 前次尝试确认终止且重复副作用安全时，创建新的 attempt_no、新 requestID 和新的输出目录。若无法证明安全，保持待核或等待研究员决定；不自动重复发通知、写结果或调用外部服务。
6. 状态变化记录在 task_events，批准、拒绝和有效范围记录在 approval_decisions，二者不可混用。FAILED 后重试需建立新的业务任务而非重启旧失败任务。所有状态更新用 version 条件检查；数据库事务只覆盖短时原子操作，不覆盖模型运行或人工等待。

## 4. Day 5 验证情景

- 连续两次提交同一个 requestID 与同一会话，应读取同一回执，不产生两个执行。
- 断开 SSE 后重新连接，不新建 Agent 任务。
- 运行期间生成结果后模拟中断，不覆盖已存在的科研文件。
- 对不确定的外部副作用，状态保持 RECONCILING 或 WAITING_FOR_CONFIRM。
- 未经授权的调用、过期批准、旧 Snapshot 和重复点击均不得解除人工等待。
- 创建时缺原始数据的任务直接进入 WAITING_FOR_DATA；FAILED 后恢复创建新任务并保留原失败记录。
- 双击启动或并发启动，同一任务不得存在两个未决 attempt。

以上均为验收目标，不代表仓库已经实现这些功能。

## 5. 科研评价状态与执行状态分离（2026-11-11）

2026-11-11 [科研研究深度调研](../03-调研与复审/07-科研工作流研究深度与质量评测调研报告-2026-11-11.md) 提出 `BLOCKED`、`REVISING`、`STOPPED_NO_GAIN`、`PAUSED_BUDGET`、`NOT_ACCEPTED` 等研究质量/停止标签；**这些不直接成为新的研枢业务状态**。现有八状态任务机与 OpenScience 运行状态仍按第 1–3 节执行。

- `BLOCKED` 是**已确认科研事实/安全阻断的质量门槛**，可与 WAITING_FOR_CONFIRM、FAILED 或完成执行但拒绝科研交付等不同业务状态同时存在；应保留验证证据与人工处理。
- `REVISING` 属于成果版本/修订操作；科研内容修改要新版本及独立复测，不靠将已完成 Agent attempt 强制改成 RUNNING。
- `STOPPED_NO_GAIN` 与 `PAUSED_BUDGET` 是研究步骤停止原因；保留科研覆盖盲区、预算依据和人工接管入口，不暗改为 COMPLETED（科研质量达标）。
- `EVALUATION_INCOMPLETE`、`SCIENTIFIC_FACT_FAIL`、`SCIENTIFIC_QUALITY_FAIL` 是**验收结果分类**，不推断 OpenScience 是否已执行成功。
- 重要科学方向、工艺/安全或资料外发范围的修改仍需有效授权；普通低风险且预先许可的任务尽量自动执行，但不得由执行状态推断已取得科学审批。

测试要确认“Agent run completed，但缺关键实验条件、科研结论有误或评分阈值未批准”均不能展示为**科研质量已通过**。适用科研深度与子项规则见 [科研深度通则](../02-实施与评测/08-科研任务深度与质量评测通则.md) 和 [实验规划评分](../02-实施与评测/09-动态实验规划与科学决策评分.md)。
