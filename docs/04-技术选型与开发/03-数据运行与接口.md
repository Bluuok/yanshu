## 研枢 V1 数据库设计

版本：2026-11-06；状态：待实施的设计规范。本文只描述数据结构，不附建表脚本。

### 1. 边界与原则

研枢保存科研项目、业务任务、人工批准、原始资料、计算依据、论文论断和证据关联。OpenScience 保存自己的 Research Agent 会话、运行回执和工具记录；研枢只保留必要的外部关联 ID。V1 在 Ubuntu 实验室工作站使用**单机 SQLite**，Windows 用户通过应用接口访问而非直接打开远端数据库文件；未来多人协作/多租户是**架构扩展边界**，本月不实现生产级并发或租户隔离。未来是否迁移 PostgreSQL 由真实需求决定。

原始科研文件必须按字节不可覆盖保存，并计算 SHA256。目录只读依赖操作系统权限或受限执行环境，路径字段不能代替实际权限。计算产物必须保存自身哈希。工程日志和科研证据分别保留，不能用 Trace 代替来源。

### 2. 核心实体与字段

| 表 | 关键字段 | 关系与要求 |
|---|---|---|
| projects | project_id、title、data_policy、created_at | 根项目；data_policy 区分公开、本地保密、获准云处理 |
| yanshu_tasks | task_id、project_id、task_type、yanshu_status、checkpoint_json、input_bundle_sha256、version、retry_of_task_id、updated_at | 一个科研业务步骤；状态、检查点、输入版本由研枢负责 |
| task_attempts | attempt_id、task_id、attempt_no、os_session_id、os_request_id、os_run_id、request_payload_sha256、attempt_state、side_effect_state、result_ref、failure_reason | 一次向 OpenScience 的执行尝试；同一任务可有多次已核对的尝试 |
| task_events | event_id、task_id、old_status、new_status、actor_type、actor_id、reason、created_at | 任务状态变化审计，不替代可追踪的人工审批记录 |
| scientific_sources | source_id、project_id、source_type、original_name、immutable_path、file_sha256、file_size_bytes、source_version、parent_source_id、provenance | 原始文件和来源版本；PDF、CSV、Excel、API 资料均可登记 |
| compute_records | record_id、project_id、task_id、attempt_id、script_version、script_sha256、environment_fingerprint、input_params、output_manifest、compute_status | 一次可追溯计算；输出清单含路径、类型、哈希 |
| compute_inputs | input_id、record_id、source_id、source_locator、parsed_data_sha256、parser_config | 多个计算输入与原始文件的数据范围、解析规则 |
| scientific_claims | claim_id、project_id、claim_text、claim_type、document_version、review_state | 同一论文不同版本的论断独立记录 |
| evidence_links | link_id、claim_id、source_id、record_id、fact_id（引用实验事实时填写）、source_locator、exact_snippet、support_state、reviewer_id | 多对多关系；论文的实测事实论断须能回查同一 ExperimentFact、来源与计算记录 |

| approval_requests | approval_id、project_id、task_id、attempt_id、request_kind、os_session_id、os_run_id、os_pending_request_id、observed_sequence、task_version、plan_version_id、scope_json、requested_by、created_at、expires_at、status、version | 绑定某次执行或实验计划版本、操作范围、有效期和快照版本。os_pending_request_id 是权限或问题请求 ID，不是 prompt 的 os_request_id |
| approval_decisions | decision_id、approval_id、decision_operation_id、decided_by、decision、decided_at、decision_scope_hash、delivery_status、os_decision_receipt_ref | 记录研究员的实际决定和投递结果；同一 approval_id 只能有一个有效最终决定，重复点击不得再次发送 |

**关键关联**：projects 与任务和来源是一对多；yanshu_tasks 与 task_attempts 是一对多；compute_records 与 scientific_sources 通过 compute_inputs 多对多关联；scientific_claims 与来源或计算记录通过 evidence_links 多对多关联。evidence_links 必须至少指向一个来源或计算记录，且不得跨项目关联；若关联 fact_id，还须核验 Fact 所属项目、试样、单位、verification_state、source_id 与原始哈希一致。

### 3. 状态与数据约束

1. yanshu_status 限定为 PENDING、RUNNING、WAITING_FOR_DATA、WAITING_FOR_CONFIRM、RECONCILING、COMPLETED、FAILED、CANCELLED。OpenScience 的运行状态单独放在 task_attempts 中，不直接覆盖业务状态。
2. task_attempts 中 attempt_no 在同一 task_id 内唯一；os_request_id 的幂等作用域是同一 os_session_id。已知活跃尝试不得并发提交第二次；未知提交状态先核对。
3. 每次更新 yanshu_tasks 必须比较 version，更新成功后版本递增；短事务内记录 task_events。等待用户或模型时不长期持有数据库锁。
4. compute_inputs 的 source_locator 可记录 CSV 稳定行标识、列及解析版本，或 PDF 页码、段落及精确片段。数据行位置不得脱离源文件哈希独立解释。
5. 原始文件与计算结果都保存 SHA256，记录生成或读取方式。科研输出需要核验后才能提升到可信状态；不能因 Agent 结束就认为论断得到支持。
6. 原始来源记录数据许可、获取时间、是否公开及授权。服务层核验 project_id 一致性；普通外键不足以保证复杂跨表引用属于同一项目。
7. 任务创建时可直接进入 WAITING_FOR_DATA，不需要先产生 OpenScience attempt。FAILED 和 CANCELLED 是终态；如果研究员显式重开失败任务，创建新 task_id，用 retry_of_task_id 关联原任务，不允许直接从 FAILED 变回 PENDING。同一未终态任务仅可在 RECONCILING 确认安全后建立新 attempt。
8. approval_requests.status 至少包含 PENDING、DECIDED、EXPIRED、REVOKED、STALE；approval_decisions.decision 至少包含 APPROVE、REJECT、REQUEST_CHANGES。审批由授权研究员触发，要求任务/计划版本一致、申请未过期、scope_json 的路径、工具、数据范围、权限范围与原请求一致。采用 version 条件更新和 decision_operation_id 去重。
9. 研枢审批已确认不代表 OpenScience 的 live permission/question 已送达。delivery_status 应区分待投递、已确认、失败和结果未知；只有在最新 Snapshot 确认 os_pending_request_id 仍有效时才调用 runtime.decide，返回 indeterminate 时核对回执而不盲重试。

### 4. 首周评审与后续范围

Day 1 研发 B 交付字段字典和实体关系草图，研发 A 确认与 OpenScience ID 映射。Day 2 建库由研发按本文执行，本文不提供或提交 SQL。Day 5 应人工检查外键、唯一性、跨项目隔离、一次计算的输入与输出哈希、同一任务重复提交和审计记录。

实验排程按以下最小契约实现，字段在首周确定，按最新《首月计划》**Day 6–23 并行设计/开发、Day 24–30 测试**。不提供建表 SQL。

| 表 | 最小字段 | 约束与含义 |
|---|---|---|
| experiment_plans | plan_id、project_id、title、active_version_id | 计划稳定 ID，active_version_id 指当前唯一有效版本 |
| plan_versions | plan_version_id、plan_id、version_no、parent_version_id、status、change_reason、approval_id、created_at、activated_at | 版本状态 DRAFT、PENDING_APPROVAL、ACTIVE、SUPERSEDED、REJECTED。未获有效审批的候选版本不得激活 |
| plan_tasks | plan_task_id、plan_version_id、stable_task_key、title、earliest_start_utc、latest_finish_utc、planned_start_utc、planned_end_utc、duration_min、constraint_rule_ref、required_resources、task_state | 记录计划任务的稳定标识、时间窗、工艺时长、设备与人员要求 |
| plan_dependencies | dependency_id、plan_version_id、predecessor_key、successor_key、dependency_type、minimum_lag_min | 同版本内的前置依赖，必须检查自环、环路与最小工艺等待时间 |
| resource_bookings | booking_id、plan_version_id、stable_task_key、resource_id、start_utc、end_utc、capacity_units、booking_state | PROPOSED、ACTIVE、CANCELLED；激活前检查设备/人员容量及时间冲突 |
| experiment_feedback | feedback_id、plan_id、stable_task_key、event_type、actual_time_utc、source_record_ref、submitted_by | 实验完成、失败、延期或新数据的事实反馈，与计划建议分离 |
| plan_change_records | change_id、plan_id、from_version_id、to_version_id、feedback_id、affected_task_keys、before_after_summary、reason | 记录局部重排原因、受影响任务、新旧版本与差异 |
| notification_events | notification_id、plan_version_id、stable_task_key、event_type、scheduled_at_utc、time_zone、idempotency_key、status、attempt_count、delivered_at、cancel_reason | 只有生效版本可以产生正式提醒；幂等键对版本、任务、事件和触发条件唯一 |

激活计划时检查同一个 plan_id 只有一个 ACTIVE 版本，审批对象的 plan_version_id 与候选版本匹配，并在事务中替换 active_version_id。计划任务依赖必须构成有向无环图；工艺硬约束不能因截止日期而缩短。资源 booking 在候选阶段只记录 PROPOSED，批准时才检查并激活正式资源占用。

收到实验反馈后，只重算受影响的后继任务，写入 plan_change_records 并保留旧计划；不可把计划状态当成真实实验结果。新计划未批准前不发送新提醒。旧版本替换时取消尚未发送的旧 notification_events，重复反馈或服务重启不得制造重复通知。时间保存 UTC 与 IANA 时区，SENT 不代表研究员已读或完成实验。

### 5. 单机 V1 的扩展约束（2026-11-10）

- 保留明确 project_id、source_id、task_id、actor 标识和版本字段，避免未来迁移时所有记录都变成匿名自由文本；**暂不建设角色权限后台或真实多租户**。服务层严格核对项目归属，重要操作留下研究者审批主体与范围。
- SQLite 启用 foreign_keys，关键唯一索引和任务版本条件更新；由应用服务串行管理会影响计划版本激活与通知去重的事务；Windows 远程端不可直接通过共享目录写 SQLite 文件。
- 论文任务应保存目标期刊、稿件类型、规则包版本和适用稿件阶段；版本产物与格式报告保持关联。必要字段可挂在明确的稿件配置对象上，**不额外强制新建复杂期刊数据库**。
- 计划需要供交互甘特图查询的 task stable key、时间窗、资源、依赖与版本差异；具体可视化偏好不是科研数据库的事实来源。
- Trace/观测表只存运行关联和索引，不把原始论文、完整实验数据或模型思考过程重复写入另一套不受控的日志库；独立科研证据仍由 scientific_sources / compute_records / evidence_links 持有。
- “逻辑实体的规范清单”与“首月需要逐一物理建表”不可混为一谈。需要独立唯一性、外键、事务和追溯的实体应单独建表；轻量配置可以采用结构受验证的 JSON，但审批/版本/来源隔离不得退化成无约束 JSON。

### 6. 科研任务深度、实验事实与计划版本的逻辑边界（2026-11-11）

> 根据 [科研深度与质量评测通则](../03-科研质量与样本/01-科研深度与评测方法.md#src-11) 与 [实验规划科学决策评分](../03-科研质量与样本/03-实验规划评分.md#src-14) 补充业务语义。仅规定应保留的证据关系，**不要求首月新增大量表或在本文件提前编写 SQL**。

1. 科研任务应能关联研究类型、当前科学问题/假设、目标深度和必需证据项、来源/授权与规则版本；“A/B/C 研究深度标签”只是诊断属性，不覆盖八状态业务状态机，也不等于样本 A/B/C 资料分级。
2. 实验计划版本 `plan_versions/plan_tasks` 表达**提议如何做**；已开展实验的真实事件 `experiment_feedback` 与来源记录表达**实际发生了什么**，必须有稳定试样/任务身份、来源/确认状态，不能依靠 `plan_tasks.task_state` 的可回滚字段作为唯一真实依据。修订/撤销计划不删除真实反馈；候选结果不可写进已完成事实。
3. `resource_bookings.resource_id` 应对应受控的**资源主数据契约**：资源类型、容量、可用/维护窗口、人员需求、授权来源及版本；资源未知时不应默认全天可用、容量无限。具体资源实体如何物理存储待开发设计，但必须能解释冲突来源。
4. 候选科研行动应保留所回答的科学问题、替代解释/预期观察、输入数据、依据、资源风险及研究者审批状态。能从计划变更记录回到“哪项新实验事实导致哪项科学建议”，不只是一个重排日期。
5. 按论文/实验分别保留评分规则版本、适用项分母、PASS/PARTIAL/FAIL/N/A/UNVERIFIED/BLOCKED、证据定位、专家签署与结果分类；Trace/Agent 执行状态不能取代科研证据。正式表字段与迁移方式在实施方案决定。

**状态语义不可混淆**：`SCIENTIFIC_FACT_FAIL`、`SCIENTIFIC_QUALITY_FAIL`、`EVALUATION_INCOMPLETE` 是科研验收结果，不是 `yanshu_status` 枚举的新增值；“修订/无新证据停止”属于研究行为或结果，不能无迁移方案扩写既有任务状态。

### 7. 跨模块科研事实、假设、科学建议与计划变更的最小契约（2026-11-17 审查补充）

**目的**：让 DATA、PLAN、PAPER、QUALITY 使用同一科研事实，不能把 Agent 文字、模拟反馈或计划任务状态当作已开展实验。下面是**逻辑对象与必需语义**，不是已定的 SQLite 物理建表清单、科研理论或已获导师批准的实验参数。字段可由已有实体＋经验证的结构化对象实现，但必须保持稳定标识、版本、出处和权限。

| 逻辑对象／主要写入者 | 最小字段（语义） | 不可破坏的关系 |
|---|---|---|
| Hypothesis / 研究者确认，PLAN 保存 | hypothesis_id、project_id、research_question、statement、version、status（PROPOSED/CONFIRMED/RETIRED）、approved_by、approved_at、source_refs | 科研假设版本固定；新结果只能指向此前存在的版本，不能事后改写假设以迎合结果。未批准假设不等于真实科学结论 |
| ExperimentFact / DATA 收集、研究者核实 | fact_id、project_id、sample_or_batch_id、experiment_run_key、stable_task_key、event_kind、observed_at、measurement_ref、measurement_value（若适用）、unit、conditions_ref、source_id、source_locator、source_sha256、authenticity（REAL/SIMULATED）、verification_state（UNVERIFIED/VERIFIED/REJECTED）、verified_by、verified_at、supersedes_fact_id | 原始记录不可覆盖；核正错误时新事实引用旧 fact_id 并保留原因。真实与模拟永不可不经标识地混合，不能单靠 Agent 断言 VERIFIED |
| ScientificAction / PLAN 提议、QUALITY 辅助复核 | action_id、project_id、trigger_fact_ids、hypothesis_id＋version、competing_explanations、proposed_step、expected_observation、evidence_refs、uncertainties、resources_and_risks、review_status、reviewer、reviewed_at | 只是待审核的**科学建议**，不是实验已经实施或假设得到证明；解释和下一实验需要追踪到真实事实与已确认假设 |
| PlanChange / PLAN 建议、研究者/预授权规则批准 | change_id、plan_id、from_version_id、to_version_id、trigger_fact_ids、action_ids、affected_task_keys、before_after、constraint_check_ref、approval_id_or_policy_grant、activation_state、activated_at | 候选与生效版本分开；已发生实验事实不随计划回滚；科学重要变更必须有有效人工批准，预授权低风险日期变化须有可查批准策略与有效范围 |

**稳定身份**：fact_id、hypothesis_id、action_id、change_id 全局或项目内唯一且引用时显式带 project_id；sample_or_batch_id 对应获确认的试样/批次，stable_task_key 对应计划跨版本稳定任务。没有试样映射、单位或原始记录的事件只能保留待核状态，不能作为 T11 的真实科学结果验收。测量值可能是结构化数组/图表而非单一浮点数，必须通过 measurement_ref 指向已哈希的原数据，不可仅写自由文本。

**与现有反馈和论文证据的映射**：`experiment_feedback.feedback_id` 是已发生事件的原始业务反馈标识；若它包含科研测量，应与 `ExperimentFact.fact_id` 通过稳定映射关联（同一 project_id、stable_task_key、source_id），可由同一持久化记录或受控关联对象实现，**不得保存两份彼此冲突的事实**。纯延期等无测量事件不必虚构 measurement_value。PAPER/QUALITY 的 `scientific_claims → evidence_links → fact_id → source_id/measurement_ref` 必须可追溯到同一已哈希原件；只有 `REAL + VERIFIED` 的 Fact 能支持“已实测”类论断，科学解释仍需独立核查与合法使用授权。新增跨线回归 `TEST-T11 → TEST-T06`：同一真实 Fact 经计划生成科学建议并进入论文 Results 后，核对试样、单位、来源哈希、版本与核验状态完全一致；模拟或未核实 Fact 不得被改写成论文真实测量。

**流程**：原始记录和权限核查 → DATA 登记 Fact（先 UNVERIFIED）→ 研究者/授权来源核实并标 VERIFIED → PLAN 对比事前已确认 Hypothesis → 提出多个有条件的 ScientificAction → 工艺/容量/先后等确定性检查 → 重要变更申请 approval_requests，或核对已有低风险预授权 → 创建候选 plan_versions 与 PlanChange → 获有效授权后原子激活并更新有效提醒 → PAPER 只引用已批准来源和可定位计算，QUALITY 独立标记推理未证实处。对结果与假设关系存在科学争议时即使 Fact 已 VERIFIED，也不能自动标记 ScientificAction 科学正确。

**仅供数据契约测试的虚构关联示例（SIMULATED，不是已做实验或实测分数）**：
- 假设 H-v1：事前登记“试验变量 X 的变化可能提高某指标”；状态 CONFIRMED；引用研究者确认记录
- 事实 FACT-demo：试样 DEMO-S1、来源演示文件 DEMO-RAW、单位由数据字典确认、authenticity=SIMULATED、verification_state=UNVERIFIED；演示反馈与 H-v1 的预测方向不同
- 建议 ACT-demo：引用 FACT-demo 与 H-v1，提供“核对仪器与单位”“根据适用方法安排复测/有区分力的对照”两项待核候选和不确定性
- 变更 CHANGE-demo：引用 ACT-demo，影响任务 T-next，生成候选计划 V2；重要实验条件未获授权时 V1 保持 ACTIVE，V2 不得激活
- **验收区别**：上述示例只验证映射、权限、回滚及状态；T11 科学效果核心验收必须另用有真实、获授权、可核对记录的 Fact，由研究者/导师评价建议。

### 8. 论文稿件、缺资料、审查和定点修订契约

| 逻辑对象／责任模块 | 最小字段及关系 | 完成前必须检查 |
|---|---|---|
| ManuscriptVersion / PAPER | manuscript_id、project_id、version_id、parent_version_id、research_type、target_journal、article_type、submission_stage、journal_rule_version、status、created_by、created_at | 每次新版本不可覆盖旧版本；导出与审查均绑定 version_id |
| ManuscriptSection / PAPER＋UI | section_id、version_id、section_type、order、content_ref、content_hash、linked_claim_ids、manual_edit_version | 章节来源和人工编辑可定位；AI 修订要检查编辑版本冲突，不得静默覆盖研究者修改 |
| MissingInputRequest / PAPER＋TASK | request_id、project_id、manuscript_id、affected_section_ids、required_field、reason、priority、acceptable_source_types、status（OPEN/ANSWERED/UNAVAILABLE/RESOLVED）、answer_source_ids、resolved_at | ANSWERED 不等于已验证；资料到达经来源/单位等核查后才 RESOLVED，依赖步骤再恢复，其他无关步骤可继续 |
| ReviewIssue / QUALITY | issue_id、manuscript_version_id、section_id、claim_id、criterion_id、evidence_locator、severity、finding、status（OPEN/FIXED/WAIVED/NEEDS_EXPERT）、reviewer、resolution_version_id | 原稿问题定位到具体版本与证据；没有依据不能将主观模型意见当确定事实；新版本的修复要独立复测 |
| ExportConfig＋ExportArtifact / PAPER | export_id、manuscript_version_id、journal_rule_version、format（DOCX/LATEX）、template_or_style_version、artifact_path、artifact_sha256、validation_report | DOCX 和 LaTeX 可以来自同一结构化稿件，但必须分别核验打开/编译及正文、公式、图表和引用的内容对应 |

**修订事务语义**：以 expected_version_id＋expected_section_edit_version 提交变更；若研究者在生成和提交之间修改了章节，返回 VERSION_CONFLICT，保留两个修改建议并请用户确认，不能覆盖人工编辑。审查可发现软件已完成但科研质量未达标的稿件，科学质量标签不得写回八状态机冒充任务状态。

### 9. 实验资源、提醒与版本状态契约

- **Resource**：resource_id、resource_type（DEVICE/PERSON/OTHER）、name、capacity_units、capability/qualification、source_ref、source_version、verified_by；**AvailabilityWindow**：resource_id、start_utc、end_utc、availability_kind（AVAILABLE/MAINTENANCE/UNAVAILABLE）、capacity_units、time_zone、source_version。未经确认的设备日历只能当占位，不能宣称资源“无限可用”。
- **Booking**：沿用 resource_bookings，必须注明资源需求量、开始/结束、计划版本、候选/有效状态；对同一容量池在重叠区间校核有效预订之和不超过已核准容量，维护/不可用窗口不得被覆盖；跨项目权限和资源数据来源要可追溯。甘特图是这一事实的视图，不是新的资源数据来源。
- **通知**：一条通知分开记录**投递状态**（QUEUED/SENDING/DELIVERED/FAILED/CANCELLED）、**用户处理状态**（UNREAD/READ/ACKNOWLEDGED/SNOOZED）和**科研任务事实**（从 experiment_feedback 判定，不由通知按钮推断）。保存 notification_id、version_id、acknowledged_by/at、read_at、snooze_until、last_delivery_error、next_retry_at、attempt_count、idempotency_key。
- **处理规则**：已读不等于确认、确认不等于实验已完成、延后不修改科研计划版本；失败投递按已批准的有限重试策略处理且禁止重复有效消息；新版本生效后取消过期未投递提醒，旧通知历史保留；重启后先核对已发送状态再补处理过期事项，不能声称断电期间已成功投递。
- **提交与外部副作用边界**：SQLite 短事务原子更新当前计划版本、有效资源占用、旧提醒取消以及新 `notification_events` 的 `QUEUED` 待投递记录；提交成功后，Ubuntu 本地调度器才按 `idempotency_key` 投递并回填状态（现有通知记录兼作 outbox，不另建消息队列）。浏览器/外部通知渠道不能被纳入 SQLite 事务；崩溃或结果未知时先核对可用投递回执，再有限重试，不得直接断言已送达或重复发送。
- **授权**：普通时间调整若可自动生效，必须有研究者此前批准的规则、作用域、有效期和审计记录；没有此类授权时仍需走有效审批，不得把“低风险”解释为无权限要求。

## 研枢 V1 任务状态与安全恢复规范

版本：2026-11-06；状态：待实现。业务状态在研枢，Agent 运行状态在 OpenScience。

### 1. 状态定义

| 研枢状态 | 使用条件 | 后续处理 |
|---|---|---|
| PENDING | 已创建且必要输入已验证，未启动；或安全核对后允许重试 | 经授权启动 RUNNING；缺输入转 WAITING_FOR_DATA |
| RUNNING | 有正在执行或已接收的运行尝试 | 成功核验后 COMPLETED；缺资料或确认时暂停；中断时进入 RECONCILING |
| WAITING_FOR_DATA | 创建时就缺少关键输入，或执行后发现缺项 | 研究者补齐并校验后返回 PENDING；不需预先建立 Agent attempt |
| WAITING_FOR_CONFIRM | 重大实验修改、数据外发或科学争议待决 | 研究者批准后继续；拒绝则退出或修改方案 |
| RECONCILING | 请求结果不确定、执行崩溃或副作用未核清 | 核对回执和产物后完成、重试、失败或等待确认 |
| COMPLETED | 成果已保存，完成业务层的指定核验 | 终态；修订创建新版本 |
| FAILED | 已确认失败、封存原因 | 终态。研究者如需重试须新建 task_id，用 retry_of_task_id 关联原任务 |
| CANCELLED | 研究者或政策终止 | 终态 |

初次输入缺失时直接创建 WAITING_FOR_DATA 状态的任务，不应提交空输入给 OpenScience。FAILED 和 CANCELLED 视为业务终态，不允许 FAILED 直接跳回 PENDING；只有未终态的 RECONCILING 任务经过副作用核对后可以新增 attempt。

不能靠轮询、定时器或模型推测绕过 WAITING_FOR_CONFIRM。非关键参数缺失允许其他独立步骤继续；关键事实缺失才阻断相应步骤。

### 2. OpenScience 状态映射

OpenScience 接收请求可能处于 accepted、running、completed、failed、cancelled、interrupted。接收成功只表示任务被接纳。completed 只表示 Agent 回合完成；科研数据、图表、引用、产物提交和必要审批仍须独立核查。interrupted 不表示可以安全重做。

### 3. 安全执行与恢复

1. 任务下发前先保存 os_session_id、os_request_id、完整请求摘要及 PREPARED attempt。OpenScience 同一 session 的重复 requestID 可返回既有回执，但不能保证外部工具副作用只执行一次。
2. 保存返回的 os_run_id，使用同版本 SDK 的 Snapshot 和 SSE 事件观察；事件断档先重新取快照，不提交第二个 Prompt。
3. 若运行中等待权限或用户问题，先建立持久化 approval_requests，并保存任务版本、权限 scope、有效期、申请人、当前 Snapshot 序号和 os_pending_request_id。只有授权研究员能提交 approval_decisions；决定需要按 approval_id 和 decision_operation_id 去重。只对最新 Snapshot 中仍有效的 continuation 调用 runtime.decide，单独保存 OpenScience 决定回执或不确定状态。服务器崩溃后不能沿用失效的审批请求。
4. 发生进程退出、网络结果未知或 interrupted 时，设置 RECONCILING。检查已提交产物、文件 SHA256、外部作业状态与可能的副作用，再决定完成或重试。
5. 前次尝试确认终止且重复副作用安全时，创建新的 attempt_no、新 requestID 和新的输出目录。若无法证明安全，保持待核或等待研究员决定；不自动重复发通知、写结果或调用外部服务。
6. 状态变化记录在 task_events，批准、拒绝和有效范围记录在 approval_decisions，二者不可混用。FAILED 后重试需建立新的业务任务而非重启旧失败任务。所有状态更新用 version 条件检查；数据库事务只覆盖短时原子操作，不覆盖模型运行或人工等待。

### 4. Day 5 验证情景

- 连续两次提交同一个 requestID 与同一会话，应读取同一回执，不产生两个执行。
- 断开 SSE 后重新连接，不新建 Agent 任务。
- 运行期间生成结果后模拟中断，不覆盖已存在的科研文件。
- 对不确定的外部副作用，状态保持 RECONCILING 或 WAITING_FOR_CONFIRM。
- 未经授权的调用、过期批准、旧 Snapshot 和重复点击均不得解除人工等待。
- 创建时缺原始数据的任务直接进入 WAITING_FOR_DATA；FAILED 后恢复创建新任务并保留原失败记录。
- 双击启动或并发启动，同一任务不得存在两个未决 attempt。

以上均为验收目标，不代表仓库已经实现这些功能。

### 5. 科研评价状态与执行状态分离（2026-11-11）

2026-11-11 [科研研究深度调研](../05-研究报告与归档/01-科研深度调研报告原文.md#src-26) 提出 `BLOCKED`、`REVISING`、`STOPPED_NO_GAIN`、`PAUSED_BUDGET`、`NOT_ACCEPTED` 等研究质量/停止标签；**这些不直接成为新的研枢业务状态**。现有八状态任务机与 OpenScience 运行状态仍按第 1–3 节执行。

- `BLOCKED` 是**已确认科研事实/安全阻断的质量门槛**，可与 WAITING_FOR_CONFIRM、FAILED 或完成执行但拒绝科研交付等不同业务状态同时存在；应保留验证证据与人工处理。
- `REVISING` 属于成果版本/修订操作；科研内容修改要新版本及独立复测，不靠将已完成 Agent attempt 强制改成 RUNNING。
- `STOPPED_NO_GAIN` 与 `PAUSED_BUDGET` 是研究步骤停止原因；保留科研覆盖盲区、预算依据和人工接管入口，不暗改为 COMPLETED（科研质量达标）。
- `EVALUATION_INCOMPLETE`、`SCIENTIFIC_FACT_FAIL`、`SCIENTIFIC_QUALITY_FAIL` 是**验收结果分类**，不推断 OpenScience 是否已执行成功。
- 重要科学方向、工艺/安全或资料外发范围的修改仍需有效授权；普通低风险且预先许可的任务尽量自动执行，但不得由执行状态推断已取得科学审批。

测试要确认“Agent run completed，但缺关键实验条件、科研结论有误或评分阈值未批准”均不能展示为**科研质量已通过**。适用科研深度与子项规则见 [科研深度通则](../03-科研质量与样本/01-科研深度与评测方法.md#src-11) 和 [实验规划评分](../03-科研质量与样本/03-实验规划评分.md#src-14)。

## 研枢与 OpenScience 接口契约 V1

版本：2026-11-10；状态：待实测的接口约定。产品目标已确定为 Ubuntu 实验室工作站运行、Windows 客户端访问，并对 OpenScience 前端进行较大幅度改造；首周需固定 runtime/SDK 匹配版本。**是否深度 Fork、如何接入前端和远程访问方式尚未定稿**。

官方依据：[OpenScience Runtime SDK and API](https://github.com/synthetic-sciences/openscience/blob/main/frontend/docs/src/content/openscience/api.mdx)、[Headless server hosting](https://github.com/synthetic-sciences/openscience/blob/main/frontend/docs/src/content/openscience/server-hosting.mdx)。

### 1. 职责

研枢负责项目数据授权、科研任务、检查点、确认流程、证据关系、材料规则与独立审查。OpenScience 负责 Research Agent 执行、模型/工具、会话、运行回执及自身权限。V1 优先 SDK、HTTP 和 SSE；没有官方依据时不另造 Webhook，也不自建第二套 Agent 循环。

| 研枢业务接口草案 | 预期作用 |
|---|---|
| POST /api/tasks | 验证授权和输入，缺材料时允许直接登记 WAITING_FOR_DATA |
| POST /api/tasks/{id}/start | 保存请求 ID 后调用 OpenScience |
| GET /api/tasks/{id} | 返回业务状态、外部尝试与结果摘要 |
| POST /api/tasks/{id}/submit-data | 补齐资料并校验版本 |
| POST /api/tasks/{id}/confirm | 对有权限且仍有效的确认进行回复 |
| POST /api/tasks/{id}/reconcile | 检查中断回执、作业及文件副作用 |
| POST /api/tasks/{id}/retry | 未终态任务经安全核对可建新 attempt；FAILED 须新建关联业务任务 |
| GET /api/tasks/{id}/evidence | 按项目授权返回证据关联 |

**V1 其他跨模块操作最小草案（2026-11-17 审查补充）**：以下路由只是研枢业务接口的建议名称，准确协议、部署路径和程序 DTO 须在 G2 后结合技术选型冻结；但**对象标识、版本检查、权限和错误语义**须在两名开发者 Day 1–5 联合定稿，避免各自发明事实类型。所有读取/写入都要核对 project_id、用户权限和对应版本，写入返回稳定操作 ID。

| 对应功能 | 业务操作草案 | 最少输入与成功返回 | 必须覆盖的拒绝/恢复 |
|---|---|---|---|
| F02 资料导入 | POST /api/projects/{p}/sources | source_id、文件哈希、授权/数据策略、解析状态与来源版本 | 缺授权、SHA 不匹配、跨项目来源：拒绝；上传重试不能重复登记冲突版本 |
| F06 稿件与补资料 | POST /api/projects/{p}/manuscripts；POST /api/manuscripts/{id}/missing-inputs/{r}/answer | 稿件版本/章节 ID；补交 source_id、expected_request_version，返回请求验证状态和受影响章节 | 没有来源不冒充补齐；问询已关闭、版本不符拒绝覆盖 |
| F07 审查与修订 | GET /api/manuscripts/{id}/issues；POST /api/manuscripts/{id}/revisions | issue_id、稿件/章节 expected_version、修改后的新版本及证据定位 | 人工编辑期间收到过期 AI 修改须 VERSION_CONFLICT；仅修对应问题，保留原稿 |
| F08 论文导出 | POST /api/manuscripts/{id}/exports | version_id、journal_rule_version、format、生成产物哈希及格式核验结果 | 缺必需期刊规则须标“未验证格式”，不能声称已经符合目标期刊 |
| F10/F12 计划/甘特 | GET/POST /api/plans/{id}/versions | 当前 plan_version_id、稳定 task_key、依赖、资源、变更 diff、预期版本 | 冲突、工艺下限、环路、过期版本：返回可定位原因；拖拽不能直接修改 ACTIVE |
| F11 科学反馈 | POST /api/plans/{id}/facts；POST /api/plans/{id}/actions | fact_id＋source_id＋authenticity＋verification_state；action_id＋hypothesis_version＋fact_refs＋alternatives | 模拟输入不能变真实事实；未核验 Fact 不能当 T11 的真实核心验收 |
| F14 审批/激活 | POST /api/plans/{id}/versions/{v}/activate | approval_id 或有效的 policy_grant_id、expected_active_version、activation receipt | 越权、过期、错误 scope、并发激活：拒绝；仅 ACTIVE 版本、资源预订、旧提醒取消和新待投递提醒记录的**数据库内状态更替**须原子化；外部投递不在该事务内 |
| F13 通知 | GET /api/projects/{p}/notifications；POST /api/notifications/{id}/read、/ack、/snooze | notification_id、expected_version、操作 ID、处理状态及更新时间 | 重复 ACK 幂等；SNOOZE 不变更实验事实；失败投递与未读分开 |

**统一失败语义**：至少包含 UNAUTHORIZED、FORBIDDEN、NOT_FOUND、INVALID_INPUT、SOURCE_UNVERIFIED、VERSION_CONFLICT、APPROVAL_REQUIRED、CONSTRAINT_VIOLATION、EXTERNAL_RESULT_UNKNOWN；返回稳定错误代码、关联对象 ID、是否安全重试以及可定位审计号。对 EXTERNAL_RESULT_UNKNOWN 先 RECONCILING，不自动重复有副作用的操作。**示例测试**：同一 manuscript_id 的旧 expected_version 提交修订必须得到 VERSION_CONFLICT，不得覆盖新编辑；同一 ACTIVE 计划并发激活两个版本，只有一个成功，其余收到冲突并保持原事实记录。

### 2. 下发及观察

1. 检查 /runtime/capabilities 及协议支持。用固定版本的 TS 或 Python SDK，不因提交失败而盲目回退旧 API。
2. 为每个执行登记 os_session_id、os_request_id 和输入内容哈希。请求实际被接纳后补存 os_run_id；首次调用前持久化原始请求的完整标识。
3. 202 或 accepted 只代表接纳，不代表科研工作完成。观察 Snapshot、SSE 事件和最终回执；事件游标失效后重取 Snapshot 并按事件序号去重。
4. 只有授权研究者可以审批当前有效的 approval_requests。请求绑定 task_id、attempt_id、os_pending_request_id、task_version、plan_version_id、权限 scope 和有效期，decision_operation_id 防止重复提交。处理 live permission/question 前必须从最新 Snapshot 重新确认请求仍存在，调用 runtime.decide 后单独记录 OpenScience 决定回执。旧快照、越权、重复点击或已撤销的审批不得继续执行。服务进程重启后，不沿用已失效的旧授权上下文。
5. 完成后核对 resultMessageID、Results、compute jobs 及研枢证据记录，再决定业务是否 COMPLETED。

### 3. Session 工作区选择与受控文件映射

OpenScience 官方 session.create 默认建立 isolated scratch 工作区。只有显式选择 workspace: "project"，工具中的相对路径才以连接选择的项目目录为基准。模式在 session 创建后固定，不能在后续 prompt 中直接切换。官方参考：[Session workspaces](https://github.com/synthetic-sciences/openscience/blob/main/frontend/docs/src/content/openscience/sessions.mdx)。

**V1 首选 project 模式，每个 attempt 使用独立的受限工作区，不把原始资料归档目录直接设为 project。**

1. 研枢在源文件归档中保存不可变原件，给本次 attempt 创建专属工作区，包含只读 input、可写 output 与文件映射清单 manifest。受控副本或实际只读挂载来自获授权的 source_id；manifest 保存源文件 SHA256、复制后 SHA256、实际工具可访问路径和权限。
2. SDK 的 directory 指向此 attempt 的工作区，创建 session 时显式 workspace: "project"。一个 attempt 保存 os_session_id、workspace_mode、workspace_path、manifest 及 output 目录。Python 工具只通过该工作区的受控路径访问文件，不得访问原始归档或其他项目目录。
3. 实际隔离由受限进程账号、操作系统 ACL 或经测试的沙箱实现。同一操作系统账户仍可随意写 input 时，不得宣称只读安全。输出先保存到本 attempt 的暂存区，校验哈希和业务结果后才原子提交，不能覆盖其他 attempt 的产物。

**备选 isolated 模式，仅在验证附件可达后启用。** 如果使用默认 isolated scratch，会话所见附件不一定等于 Python 工具可打开的文件。必须实测附件输入的实际文件位置、访问权限和哈希，并记录到 manifest；若工具找不到数据，应修正映射，不得临时放宽原始数据权限。两种模式须在创建 session 时择一，不能在运行中隐式混用。

### 4. 文件与权限

原始输入目录必须由实际文件系统 ACL、受限账号或隔离工作区强制只读；仅在 Prompt 写“read-only”不构成安全隔离。单个 attempt 的输出有唯一目录，先校验 SHA256 和科学结果，再原子提交；失败不覆盖原始文件与已确认产物。

当前 OpenScience 的项目目录选择不等于多租户授权。官方说明已登录实例可能默认分享完整会话轨迹，Day 1 必须核对设备/账户设置与实际数据外发路径。未经授权的实验室未发表资料不能发送到外部模型或遥测服务。

### 5. 远程工作台和可观测性边界

1. OpenScience 后端和科研计算默认部署在 Ubuntu 工作站；Windows 客户端须能经获授权的浏览器或工作台入口访问，不要求 Windows 主机负责运行 Agent。明确使用者身份、网络暴露范围、传输加密、密钥保存和会话权限，不允许为了远程访问公开未加保护的 Runtime API。
2. 因主运行底座优先采用 OpenScience，其前端会进行导航、视觉、交互和甘特图改造。现有组件、插件、源码修改的工程比例通过实测与《开发实施方案》决定，不能从产品目标推断必须重写 Agent 内核。
3. 运行观测先复用 OpenScience 记录；如使用 Langfuse/OTel，必须保证 Task/Attempt/Session/Run ID 正确关联、敏感输入不泄露、观测故障不影响科研任务。见 [可观测性与第三方能力接入](04-材料规则与外部接入.md#src-24)。
4. 不把 OpenScience 的工具权限确认等同于研枢对重要科研决策的审批。普通已授权计算可自动执行；研究方向、重要实验条件变更及权限/数据外发范围扩大必须请求有效的人工审批。

### 6. G2 验收

至 Day 5，需在 Ubuntu 工作站上验证一次真实模型调用，且 Windows 客户端能按授权范围访问研枢工作台；还须验证一次 Python 工具调用、结果保存、SSE 重连、请求与运行 ID 存储、任务中断后的核对、输入目录不可写、权限审批及费用记录。必须记录选择的 session workspace 模式、实际 input/output 路径与 manifest；让工具主动尝试写入 input，须由操作系统拒绝，同时 output 可以写入、原始数据 SHA256 不变；审批的过期、重复点击和旧快照也须拒绝。仅调用脚本成功不能算 G2 通过。结果必须注明实测的 OpenScience 版本、命令、日志位置与未完成问题。
