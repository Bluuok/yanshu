# V1 工作台、视觉交互与实验甘特图验收规范

> 开发入口：[V1 开发实施计划](../02-产品与实施/00-V1开发实施计划.md) 的 Day 1–30 与第三方/UI 触发时机 + [V1 功能实施候选方案 F01/F12/F14](../02-产品与实施/00-V1实施总方案.md)。本文展开可核对的 UI/动效/甘特图验收；具体图形组件、视觉 Skills 和源码路径尚待实测。不能用静态图片取代真实甘特图。

> 2026-11-10；状态：**产品目标已确认，组件与框架实现细节待开发方案决定**。本文件描述用户可感知的行为与验收，不代表已经完成 UI 开发或确认某个甘特图 Skill 可直接交互编辑。

## 1. 产品方向

用户要求在 **OpenScience 的现有工作台基础上实质改造前端**，而非只增加独立表单。保留其有效的文件管理、会话、结果与工具能力，重新统一研枢导航、项目工作区、研究任务、论文成果、动态实验规划与审批入口；做出面向科研人员的美观界面，使用成熟 UI 组件、设计系统和经核实的美化/交互 Skills 优先加速。

Ubuntu 工作站运行后端和受控计算，Windows 用户通过获得授权的工作台入口操作。初版优先浏览器访问，是否提供桌面壳由开发方案决定；不允许为了视觉效果修改科研数据或放松安全检查。

## 2. 首月 MUST 的界面行为

| 视图 | 用户操作与可见反馈 | 验收 |
|---|---|---|
| 项目首页 | 查看研究目标、数据授权、当前进度、论文/计划入口及最近成果 | 关闭重开后能找到同一项目和任务 |
| 数据/文献 | 上传或选择有授权文件、核对名称/来源/解析缺项，区分原件与派生物 | 原件不可改、SHA256 可查、失败给出具体原因 |
| 论文任务 | 选择稿件类型和目标期刊、查看章节/图表/证据状态、补交资料、修订并导出 | 能定位缺项，至少两种期刊配置能被选择并测格式差异 |
| 实验计划 | 甘特图与表格/列表同步呈现任务、依赖、时间窗、资源与状态 | 时间和依赖与保存的计划版本一致，不仅是静态图片 |
| 审批/问题 | 明确展示请求对象、变更前后、影响和有效期；批准/拒绝/请求修改 | 未批准版本不生效，重复点击不重复执行 |
| 执行与复核 | 展示运行进度、失败/待资料/待确认、成本或链路入口和可复核产物 | 软件失败与科研质量问题分开显示 |

## 3. 复杂甘特图最小交互契约

必须能够：
1. 按日/周尺度查看较长实验计划，缩放、滚动并定位任务；支持分组或实验阶段折叠；
2. 呈现任务起止、估计时长、依赖箭头、设备/人员资源、关键工艺等待窗口、任务状态；
3. 显示延期、设备冲突、未满足前置条件和关键阻塞；科研硬约束给出原因而非仅颜色提示；
4. 反馈新进度后，展示「当前已批准计划」与「候选重排计划」的受影响任务及时间差异；
5. 拟修改任务时间或依赖时进行确定性约束校验；修改进入待审批版本，未经研究者授权不得直接覆盖生效版本；
6. 支持时间线视图和可访问的表格替代视图，保存后刷新保持一致；数据量增加时不出现明显阻塞。

**Skill 的边界：** 生成复杂甘特图的 Skill 可以帮助将实验要求转换为结构化计划、图形配置、模板或报表；但真正可编辑、可交互、可持久化的甘特图仍需要成熟前端可视化组件及计划业务接口。禁止将图片生成或 Mermaid 静态图冒充完整交互实现。

## 4. 视觉、美化与动效

- 采用统一字体层级、间距、图标、状态色、深浅主题适配、空状态和错误状态；重点改善科研结果可读性、文献定位、图表预览和长计划可操作性。
- 动效用于页面/面板过渡、运行反馈、甘特图变化提示与审批结果确认。**不靠大量动画掩盖加载、阻断或科研不确定性**；支持减少动效偏好及键盘操作。
- 长时任务明确区分运行中、等待数据、等待人工审批、失败和完成；不以仅显示转圈代替状态。
- 避免全站同时引入多个同类 UI 框架和动画库。优先使用 OpenScience 已有 SolidJS UI 组件、样式和图形库；若不满足再作最小必要替换。
- 对宽屏实验室工作站与 Windows 常用浏览器进行视觉检查；长标题、中文/英文混排、长任务列表、图表/甘特图遮挡不得导致关键操作不可用。

## 5. 完整测试周的 UI 验收

- Day 24–30 单独安排视觉一致性、真实科研使用路径、交互缺陷与动画性能修复；拍摄两路线录屏或保留可复现操作记录。
- 检查「10+ 任务、跨多天依赖、至少一个资源冲突、一次候选计划修订」的甘特图案例；与数据库版本数据人工对照。
- 至少一位真实科研使用者完成「上传数据→生成并检查论文」和「生成实验计划→反馈延期→查看差异→批准」两条路径；记录卡顿、误解、点击次数和主观易用性建议。
- 页面性能、对比度、动效时长等数值阈值在首周确定测试设备/浏览器后设定，不虚构“60fps 达标”或已通过可用性测试。

## 5A. 补充验收：复杂科研计划与可用的视觉体验（PR #6 复核）

下列要求**是现有 UI 和甘特图 MUST 的验收细化，不是额外开一个 UI 系统或提前选型**：

- **视觉基线 Day 1–5**：选定 2–3 个只供风格、信息密度和交互参考的界面样例；记录研枢首页、论文审查、实验计划三类页面统一的层级、对比度、按钮/状态、中文长文本与响应式规则；视觉参考需由负责人确认，不代表复制其设计版权。
- **UI 最早可用 Day 6–11**：先有真实项目页、任务状态、论文/实验入口及甘特图基本交互，视觉方案从一开始同步应用；不等主要功能完成后才重做整站前端。
- **复杂甘特图回归 Day 18–30**：在原 10+ 任务基础检查之外，再构建**不少于 25 个任务、多个实验阶段、至少 3 种设备/人员资源、跨日依赖、一次资源冲突和一次反馈后版本变更**的案例。对照保存的事实数据，检查滚动/缩放/折叠、依赖线、冲突定位、编辑前后差异和表格替代视图。不得为了展示流畅把硬约束、未批准版本或真实资源占用隐藏。
- **视觉/动效反馈**：运行中、等待资料、待人工批准、失败和已完成五类状态有清晰可见的区别；动效用于反馈和焦点引导，不能遮挡科研证据。测试减少动效和键盘操作，记录弱网/长中文标题和较长列表是否影响操作。
- **研究者试用**：至少一位实际科研使用者分别走完“资料→论文结果→问题修订”和“规划→新结果/延期→版本差异→审批”路径，记录误操作、找不到入口、页面遮挡、建议修复和复测。审美意见可以多样，但**关键功能是否可见可操作、信息是否真实且一致必须可检查**。
- **视觉效果不抵消科研质量**：Day 24–30 包含外观/交互修复，但源文件保护、科研计算、计划审批与真实性问题仍具有更高阻断优先级。性能阈值根据真实 Ubuntu/Windows 设备首周设定，不预写未测的帧率或响应时间。

## 6. 后续再考虑

跨端协作、复杂拖拽批量操作、多人甘特图同屏、无限制算法自动排程、全局可配置视觉主题市场不阻断 V1。首月的美化工作不能挤占最后一周科研真实性与安全回归；两者都需有完成证据。
