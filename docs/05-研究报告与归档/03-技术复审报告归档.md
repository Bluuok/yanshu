### 一、先看结论：核心策略与行动原则

外部调研报告搜集了大量有价值的成熟开源项目，其探索方向与研枢“**一个主底座 + 可插拔专业服务 + 专业 Skills + 独立客观 Eval**”的总体架构基本吻合。**我们可以将该报告作为候选项目线索库，但坚决不能照搬其中的“TOP 10 清单”一次性全量安装。**

针对导师与研发负责人的核心行动决策如下：

```
+--------------------------------------------------------------------------+
|                     研枢首月（四周）实施决策总纲                          |
+--------------------------------------------------------------------------+
  |
  +--> [1. 唯一主底座原则（既定共识）]
  |    首选实机验证 OpenScience 源码，严禁同时引入第二套 Agent 调度框架；
  |    优先评估外围插件/Skills/MCP 扩展；是否修改上游核心执行循环须结合实际接口与二开评估决定。
  |
  +--> [2. 科研真实性第一（核心底线）]
  |    文献 DOI 存在不等于支持当前论文论断；原始数据计算必须可追溯、可复现；
  |    严格区分“软件运行日志 (Trace)”与“学术科研证据链 (Evidence)”。
  |
  +--> [3. 首月严格克制范围（既定共识）]
  |    首月现金采购上限 4,000 元（包含在第一阶段总预算约 12,000 元内）；
  |    首月仅构建两条科研路线的“最小可运行原型 (PoC)”，第二个月跑通端到端，
  |    第三个月独立评测；严禁提前塞入仪器控制、工业仿真、多租户与完整 RSI。
  |
  +--> [4. 统一组件准入状态]
  |    统一收敛为五种状态：已核实接口 / 待本地实测 / 已采用 / 暂缓 / 不推荐。
  |    未经过本地实机检验的组件，一律不得标为“已采用”。
```

#### 关键技术名词初次释义（非计算机专业快速导读）

- **Agent Harness（智能体运行底座 / 宿主框架）**：负责管理 AI 会话状态、任务执行步骤、调用外部工具并处理人类确认交互的核心中枢框架。
- **SDK（软件开发工具包，Software Development Kit）**：软件官方提供的一套代码库与接口规范，方便开发者用特定语言（如 Python、TypeScript）直接调用其功能。
- **MCP（模型上下文协议，Model Context Protocol）**：业界开放的工具通信协议，允许大模型以统一、标准的方式安全调用本地文件、数据库和外部微服务。
- **Skills（专家技能包）**：遵循开放标准编写的操作指引与代码片段（以 `SKILL.md` 为核心），教会大模型按材料领域的专业步骤处理特定任务（如数据清洗、拉伸计算）。
- **Trace（运行追踪日志）**：记录大模型调用过程、花费多少 Token、耗时几毫秒、哪一步发生报错的**软件工程诊断日志**。
- **科研证据链（Claim-to-Evidence Chain）**：学术层面的证明拓扑，记录论文结果段的某一句话（Claim），究竟对应哪个原始测量 CSV 文件中的哪行数据、由哪段计算代码导出、引用了哪篇文献的具体段落。
- **Eval（独立评测与质量基准）**：独立于生成系统之外的自动化打分与人工复核机制，用于量化检验大模型写出的初稿是否真实、逻辑是否严密。
- **API Gateway（应用程序接口网关）**：介于研发平台与大模型提供商之间的反向代理，负责请求转发、多模型路由、负载均衡与额度控制。
- **Provider（模型服务提供商 / 算力通道）**：实际提供大语言模型 API 算力的服务商（如七牛云 Modelink、DeepSeek 官方等）。

### 三、外部报告中必须严肃纠偏的关键误区

#### 1. “运行核查脚本”绝不等于“证明科学内容真实”
外部报告高度推崇 K-Dense 的核查脚本（如 `verify_citations.py`、`validate_claim_evidence.py`）。
- **事实真相**：这些脚本只能检查“填报字段是否漏填”、“DOI 在 Crossref 数据库中是否存在（文献元数据真实性，即评分 Q1 维度）”。
- **致命盲区**：**DOI 真实存在，绝不代表该文献支持当前论文中的论断！** 学术中最隐蔽的幻觉是“真实存在的顶刊文献，被安放在一个它从未得出的结论后面（甚至与原文相反，即评分 Q3 维度）”。
- **研枢准则**：程序化元数据核验仅能打底；科研论断的证实，必须通过检索提取原文具体文本段落（Exact Quote Snippet）进行证据匹配，重大结论争议必须保留导师人工确认。

#### 2. 严禁混淆工程调用追踪（Trace）与学术证据链（Evidence Graph）
- **事实真相**：外部报告建议直接用 Langfuse 记录学术证据支撑。
- **概念纠偏**：
  - **Langfuse Trace** 是面向程序员的**软件工程运行日志**（记录调了哪个 API、花了多少钱、哪一行报了 500 错误），其数据具有临时性与运维淘汰周期。
  - **科研证据链** 是面向学术界与导师的**科学论据映射图谱**（记录论文第三章公式 2 的实验数据来自哪台试验机导出的 CSV 原始行、第四章对耐候性的转述对应哪篇文献第 3 页结论）。
- **研枢准则**：Trace 与证据链必须物理分离。证据链必须由研枢系统自身的关系型数据结构进行长期持久化存储与版本管理，绝不能绑定在第三方日志监控工具中。

#### 3. 腾讯开源项目（Hyra 2.0 与 Yunque）属于“架构借鉴”，绝非“现成插件”
- **腾讯 Hyra 2.0（2026-11-02）**：腾讯官方开源的 [`Tencent-Hunyuan/Hyra-results`](https://github.com/Tencent-Hunyuan/Hyra-results) 仅是科研论文的**实验结果数据集与局部复现评测代码**，根本没有开源可独立部署的完整 Agent 平台内核。研枢只借鉴其“Overall（项目目标）/ Mission（子课题）/ Worker（执行者）”的分层解耦思维，严禁将其当成可调用的软件包。
- **腾讯 YunqueAgent**：官方开源的 [`Tencent-BAC/YunqueAgent`](https://github.com/Tencent-BAC/YunqueAgent) 具备动态工具路由与 Supervisor。必须明确：**Yunque 的 Supervisor 是“工程容错监护器”**（防止模型死循环、抓取调用超时），**绝对不等同于研枢 A7 的“独立学术质量复审”**（审核数据是否真实、力学单位是否搞错）。两者不可混为一谈。

#### 4. LiteLLM 的“预算硬限制”强依赖外部数据库，无数据库等于裸奔
- **事实真相**：外部报告宣称部署一个精简的 LiteLLM Docker 即可确保不超支。
- **官方技术依据**：经 LiteLLM 官方文档证实，针对 User/Team/Key 的预算硬追踪（Max Budget Hard Limit）必须依赖外部 PostgreSQL 数据库。
- **风险暴露**：官方文档要求预算功能连接 PostgreSQL；无数据库或并发情况下的具体行为需针对选定版本实测，不能将配置值视为可靠支出上限。
- **研枢准则（复审建议）**：首月不引入 LiteLLM Proxy。物理防超支直接建立在**各模型提供商官方控制台**：在七牛云 Modelink 和 DeepSeek 后台设置硬性充值上限、每日消费限额与 API Key 独立额度，代码层增加单任务 Token 熔断计数。

#### 5. MinerU 存在在线服务署名义务，且对单机显存要求极高
- **事实真相**：经官方协议核实，MinerU 采用的是自定义的 `MinerU Open Source License`（基于 Apache 2.0），虽然商业门槛为月活 1 亿或月营收 2000 万美元（当前实验室规模远未触及），但明文包含了**在线服务署名义务**（若对外提供服务需显著标注 MinerU）；此外，其高精度多阶段视觉模型对显存要求较高（建议 8GB+ GPU 显存）。
- **研枢准则（复审建议）**：首月 4,000 元预算、单机 Windows 环境下，强行本地部署 MinerU 极易遭遇 CUDA 依赖冲突与显存溢出（OOM）。首月材料实验以结构化力学数据为主，PDF 提取优先使用Docling（代码仓为 MIT，依赖和模型许可另行核查；性能待实测）；待后续遇到极端复杂双栏扫描件时再在独立 GPU 容器中评估。

#### 6. Langfuse 完整自托管运维成本沉重，首月严禁盲目“全套自建”
- **技术依据**：根据 Langfuse 官方部署指引，完整的自托管集群需要维护：PostgreSQL（元数据与用户）、ClickHouse（分析类海量日志存储）、Redis（异步任务队列）以及 S3 兼容对象存储。
- **研枢准则**：首月 2 名研发人员，绝不能将宝贵精力消耗在单机 Windows 上搭建和维护 4 个分布式基础软件中。首月若使用 Langfuse，优先接入官方 Cloud 免费版（配置数据脱敏，禁止发送未发表敏感实验数据），或仅部署无 ClickHouse 的极简测试实例。

#### 7. 坚决剔除“零幻觉”、“保证节省 50%”等无事实依据的浮夸宣传
- **科学事实**：当前所有自回归大语言模型在概率生成机制下均存在幻觉风险。宣传“零幻觉”属于伪科学。研枢的正确路径是“**通过只读实验数据复算、DOI+原文文本定位、确定性规则拦截以及导师人工裁决，降低错误风险并通过评测量化效果**”。
- **指标纠偏**：外部报告宣称的“保证人工修改时间减少 50%”和“94.8 分综合高分”，缺乏任何真实材料实验基线数据支持。首月必须将人工修改耗时（`time_to_acceptable`）作为**待验证科学假设**进行严谨计时对比，未测前不作虚假承诺。

#### 8. 材料力学实验优先通用科学计算库，不盲目预装晶体库
- **任务匹配**：研枢首期试点聚焦于**复合材料拉伸、断裂韧性、胶接接头强度**等连续力学与宏观实验。
- **研枢准则**：首月数据分析的核心工具是成熟通用的 **Python / pandas / NumPy / SciPy / Matplotlib**。Pymatgen（材料基因组计算库）擅长晶体学 CIF、XRD、第一性原理相图分析，与首期宏观力学拉伸任务不直接匹配。坚持“按需引入”，首月不盲目预装非必需的重量级专业库。

### 二、四大架构职责切分与系统冗余排查

研枢架构的核心原则是：**“一套主运行底座（Agent Harness） + 可插拔外部服务（Pluggable Services） + 专业专家技能（Domain Skills） + 独立客观评测（Independent Eval）”**。

```
+-------------------------------------------------------------------------+
|                         研枢主工作台 (Yanshu Workbench)                  |
+-------------------------------------------------------------------------+
                                    |
+-------------------------------------------------------------------------+
| 1. 唯一主运行底座 (Agent Harness): OpenScience (TS / Bun)               |
|    - 会话生命周期、任务状态机、人机确认交互、基础工具调用循环           |
+-------------------------------------------------------------------------+
        |                          |                          |
        v                          v                          v
+------------------+      +------------------+      +---------------------+
| 2. 可插拔服务    |      | 3. 专业 Skills   |      | 4. 独立 Eval 与治理  |
| (Pluggable Svc)  |      | (Domain Skills)  |      | (Independent Eval)  |
| - Python 科学计算|      | - 材料数据清洗   |      | - A7 科研论断核验   |
| - Docling 解析   |      | - 拉伸性能复算   |      | - 独立测试集隔离    |
| - Pandoc 导出    |      | - 真实性核查脚本 |      | - 研枢关系型证据库  |
| - 学术元数据 API |      | - 投稿格式模板   |      | - Promptfoo 回归基准|
+------------------+      +------------------+      +---------------------+
```

#### 1. 四层职责边界定义
- **主底座（Agent Harness）**：仅负责 Agent 会话生命周期、任务拓扑调度、人机交互确认点以及通用的文件读写与命令执行。**严禁在底座内部写死具体的材料力学公式或特定期刊排版逻辑。**
- **可插拔服务（Pluggable Services）**：通过稳定受限的 CLI、本地 HTTP REST 或 MCP（Model Context Protocol）暴露的无状态计算/解析单元。它们只做“确定性的事”（如 Pandoc 格式转换、Docling PDF 提取、Python 脚本数据拟合），不具备自主决策权。
- **专业 Skills（Domain Skills）**：遵循开放 Agent Skills 规范（以 `SKILL.md` 为核心，包含提示词模板与轻量辅助脚本），为特定科研步骤（如材料实验数据清洗、拉伸模量复算、引文格式比对）提供上下文知识。
- **独立 Eval（Independent Eval）**：独立于执行 Agent 之外的客观检验机制（研枢 A7 职责）。必须与执行环境保持**沙箱级与数据级物理隔离**，保存标准答案与专家校准规则，绝不允许执行 Agent 自评自核。

#### 2. 必须拆除的 4 处系统级冗余隐患

1. **双调度内核冗余（OpenScience 与 OpenResearch / LangGraph 混装）**：
   - *问题*：部分资料曾设想将 OpenResearch（Rust CLI `orx`）或 LangGraph 与 OpenScience 串接。
   - *复审意见*：**建议首月避免“Agent 嵌套 Agent”**。OpenResearch 专注于计算实验的代码版本树，OpenScience 是通用科研工作台。如果主底座调度 OpenScience，OpenScience 内部又唤醒 OpenResearch 形成双重调度，可能增加上下文、调用链排障和 Token 成本，具体影响需通过实测判断。首月必须坚决以 OpenScience 为唯一探索底座，OpenResearch 仅供纯算法/目录规范参考。
2. **API 网关重复嵌套（模型直连 vs LiteLLM Proxy）**：
   - *问题*：现有采购已锁定七牛云 Modelink（含配额、Key 管理与日志）与 MaiToken，外部报告又强制插入 LiteLLM Proxy。
   - *复审意见*：首月单机开发环境下，多包一层 LiteLLM 只会徒增代理进程崩溃、异步流中断和调试网络排查成本。且在未部署 PostgreSQL 数据库时，LiteLLM 的内存配额根本无法防范并发打穿预算（官方已证实无数据库下 budget fails open）。**首月建议采用 SDK/API 适配器直连，不部署 LiteLLM 网关服务。**
3. **PDF 解析器三重堆叠（Docling + MinerU + GROBID）**：
   - *问题*：报告试图同时引入三款重型解析器。
   - *复审意见*：首月选定的材料测试论文（如 MAT-001/002/003）最核心的输入不是生僻排版的扫描件，而是带有清晰表头的数据集表格（CSV、Excel、Source Data）与规整的 Nature/Elsevier 开放 PDF。Docling 支持导出 Markdown/JSON，是否足以支撑首月验证仍待实测。MinerU（显存开销巨大、带在线服务署名义务）与 GROBID（Java 容器、侧重引文抽取）首月建议暂缓安装。
4. **把运行追踪日志（Trace）等同于科研证据链（Evidence Graph）**：
   - *问题*：期望用 Langfuse Trace 直接替代研枢学术论断—数据证据的追溯系统。
   - *复审意见*：严重概念混淆。Langfuse Trace 记录的是“第 X 步调用了什么模型、消耗了多少 Token、网络延迟几毫秒”的**软件工程日志**；而科研证据链记录的是“本篇论文结果段第 3 句声称弹性模量为 3.4 GPa，其依据对应于 `raw_data_specimen_3.csv` 经 `calc_modulus.py` 拟合得到的第 4 行数据，引文 12 对应 DOI XXXXX 的第 4 页结论”。证据链是具有学术严肃性的业务实体，必须持久化保存在研枢自己的数据库中，绝对不可寄生在临时性的 APM 追踪日志内。

### 三、唯一主二开候选 OpenScience 的审定意见

**审定结论**：**将 OpenScience 作为首选待实测候选是合理的，但必须保持“只做外围扩展，不碰核心循环”的审慎策略。**

#### 1. 合理性支持证据
- **架构对齐度高**：OpenScience 具备现代科研工作台形态（SolidJS + Bun/TS + Electron），原生支持 Agent Skills 加载、MCP 工具暴露以及科研沙箱执行，这与研枢“A0–A7 职责化”高度契合。
- **协议干净**：核心仓库遵循 Apache-2.0 许可证，商用二开与学术发布均无知识产权阻碍。
- **当前版本可核实**：官方已发布 v2.0.153（2026-10-30），具备 Windows 原生发布包。

#### 2. 明显被忽略的接口、版本与运维难点
1. **Windows 原生平台与 Bun/TS 跨语言调用壁垒**：
   - 研枢的科研分析核心（pandas, SciPy, Matplotlib）以及文档解析（Docling, PaperQA2）全部为 **Python 技术栈**，而 OpenScience 的主调度器为 **Bun/TypeScript**。
   - 在 Windows 系统原生环境下，跨进程管道调用（stdio/child_process）经常遭遇编码混乱（GBK vs UTF-8）、子进程僵死、路径斜杠转义（`\` vs `/`）等暗坑。
   - *行动建议*：首周必须用最小 Python 脚本打通与 OpenScience 的 MCP 或 CLI 通信接口，形成稳定的进程调用契约。
2. **“单机研究者”假定与未来权限隔离的冲突**：
   - OpenScience 官方架构假定为“单个科学家在本机桌面工作”，其工作区切换仅是本地文件目录切换，完全缺乏“个人未发表保密数据 vs 团队共享数据 vs 公开基准数据”的权限隔离策略。
   - *行动建议*：首月不要试图在 OpenScience 内部重构多租户体系，必须在单机环境严守“仅使用公开材料实验数据”的红线，不得把未经授权的敏感实验室数据写入测试环境。
3. **上游高速演进的二开代码维护危机**：
   - OpenScience 尚处活跃迭代期。若研发团队在首月直接对其核心代码进行大拆大改，未来上游修复安全漏洞或发布新功能时，研枢将陷入“无法 Merge、越改越死”的孤岛境地。
   - *行动建议*：**恪守 G2 关口约束**——研枢的所有增量业务功能（实验数据校验、论文初稿格式化、动态实验排程拓扑），建议一律以**独立 Skill、外部 MCP Server 或子进程插件**形式挂载，严禁侵入 OpenScience 主调度循环。

### 五、腾讯开源项目（Hyra 2.0 与 Yunque）的技术属性定位

外部报告将腾讯相关成果包装成“现成即用的顶尖插件”，存在严重的归类错误与事实扭曲，必须彻底厘清：

#### 1. 腾讯 Hyra 2.0（2026-11-02）
- **事实依据**：腾讯混元官方在 GitHub 开源的仓库为 [`Tencent-Hunyuan/Hyra-results`](https://github.com/Tencent-Hunyuan/Hyra-results)。该仓库的核心内容是科研成果的数据集、评测基准和部分复现脚本，**根本没有开源完整的、可直接运行的 Hyra Agent 平台内核代码**！
- **研枢定性**：**属于第二类：纯学术思想与架构方法借鉴**。
- **可借鉴点**：研枢可参考其 **“Overall（对齐总目标）/ Mission（负责单项科研任务）/ Worker（执行具体原子动作）”** 的分层设计，以及研究状态分层存储理念。首期研枢通过“A0 协调员 + 显式状态机”即可实现该思想，绝不能让研发人员花费精力去寻找不存在的 Hyra 软件包。

#### 2. 腾讯 YunqueAgent
- **事实依据**：腾讯官方开源了 [`Tencent-BAC/YunqueAgent`](https://github.com/Tencent-BAC/YunqueAgent)，具备主协调器、原子能力池、历史上下文压缩及 Supervisor 主动异常检测。
- **研枢定性**：**属于第二类：工程架构与局部算法借鉴**。
- **职责厘清（关键防错）**：YunqueAgent 的 **Supervisor 机制本质是“工程运行期监护器”**，用于检测模型输出格式错误、工具调用超时、上下文超长或执行死循环，目的是保障软件运行的健壮性。**这与研枢 A7 的“独立学术质量复审”具有本质区别！** A7 审核的是材料实验数据是否篡改、单位是否换算错误、引文 DOI 是否张冠李戴、结论是否违背物理常识。绝对不能因为引入了工程 Supervisor，就宣称完成了科研质量复核。

### 六、缺乏依据的虚假表述与科学打假

针对外部报告及过往规划中出现的浮夸口号，复审给出严肃的科学纠偏依据：

1. **“零幻觉保证”——伪科学命题**：
   - *打假依据*：自回归生成式大语言模型在概率采样机制下，无法在理论上消除幻觉。即便引入 RAG 或检索增强，仍面临检索未召回、上下文截断导致的断章取义、以及模型在长上下文下的推断变形。
   - *严谨表述*：应改为“**通过确定性规则过滤、论断—证据链显式锚定、反向交叉校验及专家人工核准，最大限度降低事实性与引用性错误率**”。
2. **“保证人工修改时间减少 50%”——无事实依据的凭空推测**：
   - *打假依据*：目前研枢尚未在真实的材料实验项目上完成一次端到端的人工耗时对比实验，完全缺乏计时统计 baseline。
   - *严谨表述*：必须定义为“**第一阶段的核心验证假设与追求目标**”，必须通过首月与后续实测中对 `time_to_acceptable`（达到可接受状态所需的人工修改分钟数）进行严格对照计量，未测之前严禁写入确定性承诺。
3. **“2–4 周建成生产级科研 Agent 平台”——严重脱离工程实际**：
   - *打假依据*：生产级平台需要高可用基础设施、多租户强安全隔离、严格细粒度鉴权、灾备恢复机制和工业级运维支持。首月 4,000 元预算、单机 Windows 环境、2 人研发，定位只能是“**最小可运行原型（PoC / MVP）与核心算法验证**”，第二个月争取跑通端到端，第三个月开展首期综合评测。
4. **“完全纯净的 Apache 2.0，毫无商业许可风险”——未做依赖溯源的轻率论断**：
   - *打假依据*：例如 MinerU 的官方协议是自定义的 `MinerU Open Source License`，虽然基于 Apache 2.0，但明文包含了**月活跃用户 1 亿或月营收 2000 万美元的单独许可门槛**，以及**在线服务署名义务**；许多开源 Skills 内部依赖的 Python 三方库甚至包含 GPL/AGPL 传染性协议。
   - *严谨表述*：对所有引入的组件和 Skill 必须建立三方许可证台账（LICENSE & NOTICE），逐项核验，不得做全称肯定式的免责承诺。

### 七、第一阶段两条科研路线未被覆盖的关键验收风险

#### 1. 路线 A（真实材料到论文初稿）未覆盖风险
1. **“Source Data”不等于“原始测量数据”的学术陷阱**：
   - *风险剖析*：顶刊论文（如 Nature 论文）公开的“Source Data”大多已经是经过作者二次筛选、计算均值和标准差后的汇总表（用于绘制折线图的几个数据点），根本不是从材料拉伸试验机导出的每秒几千行的原始力-位移时程数据。
   - *验收威胁*：如果用汇总数据冒充原始数据进行测试，研枢的“原始数据清洗、离群点剔除、真实力学性能拟合”核心能力根本无法得到检验。
   - *应对措施*：入库时严格执行 A 级案例标准（如 MAT-002 的 Zenodo 663 次完整拉伸原始包），必须包含仪器原始测量值；对只有汇总表的案例诚实降级为 B 类。
2. **引文元数据真实性（Q1）与论断支持性（Q3）的严重脱节**：
   - *风险剖析*：大模型最常见的学术欺骗是将一篇真实存在的名家论文（DOI 真实，Q1 满分）放在一个它从未做出的结论后面（Q3 零分）。
   - *应对措施*：评测验收必须强制要求从源论文中抽取出支持论据的具体段落文本（Exact Quote Snippet），并建立 Claim-to-Snippet 校验，不允许仅凭 DOI 正确就认定引用通过。
3. **原始数据被模型意外篡改或覆写的静默风险**：
   - *风险剖析*：代码执行器如果在当前工作区拥有写权限，模型生成的 Python 脚本可能会因逻辑错误直接修改或覆盖输入的 CSV 数据，造成后续测试虚假收敛。
   - *应对措施*：必须在操作系统层或挂载层将原始实验数据目录设置为**严格只读（Read-Only）**，所有计算产物必须重定向写入带时间戳的输出目录。

#### 2. 路线 B（动态实验规划与提醒）未覆盖风险
1. **“已发表论文 Methods”缺乏真实进度时序的先天缺陷**：
   - *风险剖析*：任何已发表论文都只展现了成功的最终方案，绝不会记录作者“哪天因为烘箱故障停工 3 天”、“哪批复合材料因气泡报废重做”。
   - *验收威胁*：如果直接拿 Methods 的步骤当实验排程，无法测试动态重排算法。
   - *应对措施*：必须在规划案例卡中明确区分“文献真实的科学步骤”与“专家人为注入的模拟异常事件（如设备预约冲突、延误 48 小时）”，必须明确标注，不得把模拟推演冒充为历史真值。
2. **违背材料物理/工艺常识的“荒谬重排”风险**：
   - *风险剖析*：纯 LLM 在接收到“总工期面临延误”的压力时，往往会通过压缩工序时长来迎合截止日期（例如擅自把必须 24 小时的室温固化压缩到 4 小时，或者在热压成型后未冷却时就安排脱模）。
   - *应对措施*：系统必须引入**工艺物理不可压缩约束包（Process Hard Constraints）**。任何涉及物理硬时间的参数不可被模型擅自压缩，遇延期只能向后顺延或报警，不能牺牲科学规律。
3. **全局重排引发的“震荡风暴”与提醒疲劳**：
   - *风险剖析*：一旦实验人员上报一个小的调整，若调度算法执行全图拓扑重排，会导致后续所有未开始的实验时间全量变动，并向研究人员发送雪崩式的“时间变更提醒”。
   - *应对措施*：明确规定**局部增量重排原则**（仅沿有向无环图的后继受影响子树调整），并强制实行“通知事件去重与失效通知自动撤销机制”。

### 八、最多 8 条最值得修改的实质性问题清单

根据独立审阅，在研枢现有核心文档中甄选出 **8 条最关键的实质性技术问题**，逐一提供事实依据与修改方案：

#### [问题 1] 混淆工程调用追踪（Trace）与学术证据链（Evidence Graph）
- **涉及文档**：[`技术调研.md`](../04-技术选型与开发/02-第三方组件调研.md#src-18) 第 2.1 节（P0 Langfuse 条目）；[`报告复核.md`](03-技术复审报告归档.md#src-28) 第 3.2 节。
- **问题本质**：试图将科研论断（Claim）、实验原始数据映射和文献支持关系直接委托给 Langfuse Trace 存储。
- **为什么有问题**：Langfuse Trace 是面向系统性能、Token 计量和 Prompt 调优的工程日志系统，其数据模型是扁平的 Run/Span 树，存在生命周期淘汰机制。而学术证据链是科研成果的核心资产，必须长期可追溯、支持细粒度版本查询。混为一谈会导致科研证据与工程日志强耦合。
- **建议改法**：明确两者的物理隔离。在 [`报告复核.md`](03-技术复审报告归档.md#src-28) 和 [`技术调研.md`](../04-技术选型与开发/02-第三方组件调研.md#src-18) 中重申：Langfuse 仅用于 Agent 运行链路追踪与 API 费用监控；科研“论断—原始数据—引文定位”的证据网必须由研枢关系型数据结构持久化保存。
- **事实依据**：[Langfuse Tracing Data Model 官方文档](https://langfuse.com/docs/observability/data-model)。

#### [问题 2] LiteLLM 预算控制前提失真（缺少数据库则硬限制失效）
- **涉及文档**：[`报告复核.md`](03-技术复审报告归档.md#src-28) 第 3.4 节；[`首月计划.md`](../02-产品与实施/01-首月V1目标与计划.md#src-7) 第 4.2 节。
- **问题本质**：部分表述认为部署 LiteLLM 即可无条件实现“严格防超支、预算硬限制”。
- **为什么有问题**：**经 LiteLLM 官方文档证实**，针对 User/Team/Key 的 `max_budget` 持久化硬限制，必须依赖 PostgreSQL 数据库存储实时花费状态。如果只运行精简的 Docker 容器而不配置外部持久数据库，则不满足官方预算功能的数据库要求；具体失效方式及并发超额风险需针对选定版本验证。
- **建议改法**：在 [`报告复核.md`](03-技术复审报告归档.md#src-28) 明确指出该先决条件；首月建议暂缓 LiteLLM Proxy 部署，改由七牛云 Modelink、DeepSeek 等服务商后台的账户预付充值和 API Key 额度作为辅助控制（以服务商实际能力为准，不保证绝对阻断），代码层辅以任务级 Token 熔断计数。

#### [问题 3] MinerU 许可证门槛与首月硬件门槛客观核定
- **涉及文档**：[`技术调研.md`](../04-技术选型与开发/02-第三方组件调研.md#src-18) 第 2.1 节 P1 表格；[`报告复核.md`](03-技术复审报告归档.md#src-28) 第 3.5 节。
- **问题本质**：将 MinerU 视为首月可直接安装的通用轻量 PDF 解析插件，或对其许可风险做模糊定性。
- **事实核定**：
  1. **许可层面**：官方采用 `MinerU Open Source License`（基于 Apache 2.0），明确限制 MAU 超过 1 亿或月营收超过 2000 万美元时需单独商业授权（首月实验室不涉及）；但包含**在线服务署名义务**，若对外提供服务需显著标注。
  2. **工程层面（核心阻碍）**：MinerU 基于庞大的视觉版面分析与多阶段 OCR 流程（LayoutLM、YOLO、公式识别等），权重数个 GB，推荐 8GB+ GPU 显存。在首月单机 Windows 且预算 4,000 元环境下，部署极易遭遇 CUDA 依赖冲突与显存 OOM。
- **建议改法**：将 MinerU 在首月明确标注为“暂缓（建议）”，首月 PDF/表格解析优先采用Docling（代码仓为 MIT，依赖许可及性能待核查）；待后续遇到极端复杂的双栏混排与复杂公式文献时，再在独立 GPU 容器中进行评估。
- **事实依据**：[MinerU 官方 GitHub 仓库及 LICENSE.md](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md)。

#### [问题 5] 误把文献元数据校验（Q1）等同于学术论断支持性核验（Q3）
- **涉及文档**：[`报告复核.md`](03-技术复审报告归档.md#src-28) 第 3.1 节；[`论文评分.md`](../03-科研质量与样本/02-论文评分.md#src-13) 第 4.1 节。
- **问题本质**：过往外部报告认为运行 K-Dense 的 `verify_citations.py` 就解决了引用幻觉问题。
- **为什么有问题**：`verify_citations.py` 仅调用 Crossref 查询 DOI 是否有效、作者年份是否匹配（即 Q1 维度的 15 分）。但科研中危害最大的幻觉是“真实存在的文献，被安放在完全不支持、甚至反驳它的假论断之后”（Q3 维度的 30 分）。元数据通过完全不等于学术真实。
- **建议改法**：在 [`报告复核.md`](03-技术复审报告归档.md#src-28) 中以醒目警示明确：元数据存在性验证只是引文核查的第 0 步；必须要求 Agent 提取引文的具体支撑文本，通过语义比对模型判断支持关系，重要争议结论必须保留人工专家裁定入口。
- **事实依据**：[K-Dense verify_citations.py 源码实现](https://github.com/K-Dense-AI/scientific-agent-skills/blob/main/skills/literature-review/scripts/verify_citations.py)。

#### [问题 7] 动态实验规划缺乏“材料工艺硬约束”与“局部重排防震荡”
- **涉及文档**：[`02-第一阶段实施规范.md`](../02-产品与实施/02-第一阶段实施规范.md#src-8) 第 3 节；[`03-总体技术架构.md`](../01-项目总览/01-建设总纲与架构.md#src-2) 第 4 节。
- **问题本质**：实验规划路线将重点全部放在了“时间计算、延期更新、通知触发”上，缺乏对材料制备物理规律的刚性约束。
- **为什么有问题**：实验规划不同于通用敏捷开发项目，材料工艺具有不可违背的物理特性（如某工艺经实验确认的最低固化时间不能为赶工而擅自缩短）。若无工艺规则引擎，纯 LLM 会在资源冲突时生成违反物理常识的荒谬排程。
- **建议改法**：在实施规范和架构说明中补充“工艺硬性不可压缩约束（Process Invariant Constraints）”定义；同时规定动态更新机制为“仅针对依赖子树的局部最小调整”，避免一次进度延期导致整个实验室日程全局大翻车。

#### [问题 8] 评测数据隔离机制缺少物理落地的沙箱措施
- **涉及文档**：[`04-资料收集与评测规范.md`](../03-科研质量与样本/01-科研深度与评测方法.md#src-12) 第 6 节；[`测试论文.md`](../03-科研质量与样本/04-测试论文与数据.md#src-15) 第 4 节。
- **问题本质**：强调了“开发集 vs 盲测集、目标论文不能进入上下文”，但缺少工程层面的防泄漏实操规则。
- **为什么有问题**：目前 12 篇测试论文已在仓库内公开罗列，开发人员在测试 Agent 时很容易将其全文或 DOI 暴露给全局检索工具，或者在构建本地 RAG 时一次性将全部 12 篇论文向量化入库，导致 Agent 提前把标准答案当成检索素材“偷看”，评测分数严重虚高。
- **建议改法**：在工程结构上建立物理隔离规范：执行端工作区（`workspace/inputs/`）仅允许存放经过去除标题、摘要、结论的清洗后纯实验数据包；隐藏评测集（`eval/ground_truth/`）单独存放，严禁建立全局向量索引；对检索工具施加目标论文 DOI 与标题黑名单。
